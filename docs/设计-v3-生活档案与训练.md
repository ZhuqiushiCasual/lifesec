## 1. 视觉方向：城市导视 / 线路图

### 1.1 为什么是这个

用户日常随手打开，训练后 / 饭后记录；回看时先按**日期**和**地点**找。线路图天然同时表达这两件事：
时间是一条线，经历是站点，地点是站名，同一天多件事是换乘。它也比「手账 / 日记本」更克制、更像工具，避开用户明确排斥的方向。

### 1.2 世界规则

| 角色 | 值 | 用法 |
|---|---|---|
| 地面 | `#F3E6D3` 暖砂 | 页面底；明确的暖砂，不是默认奶油白 |
| 面板 | `#EADBC6` | 顶栏、选中态底 |
| 卡片 | `#FFFBF3` | 卡片、输入框 |
| 墨 | `#332A22` 深棕 | 主文字、主按钮、当前 tab；**不用纯黑** |
| 次墨 | `#6B5D4F` | 元信息、次级文字 |
| 弱墨 | `#6E5E4C` | 时间戳、占位 |
| 线 | `#DFCFB8` | 1px 分隔线；线路用 2px |
| 训练 | `#5C6B3C` 橄榄 | 站点、卡头、筛选选中 |
| 吃饭 | `#B4482F` 砖红 | 同上 |
| 计划 | `#A8791C` 赭黄 | 同上 |
| 洞察 | `#7E6A56` 灰褐 | 同上；刻意弱化，洞察不是主角 |
| 一般事件 | `#7B6C5C` 暖石 | 同上 |

- **字体**：系统无衬线（PingFang SC / 微软雅黑 / Noto Sans SC）；数字与时间用 `ui-monospace` 等宽。不用 Inter / Roboto 做标题，不用衬线、手写体。
- **密度**：8pt 节奏；列表行距紧，信息密度高；一屏至少看到 3–4 个站点。
- **形状**：圆角 ≤ 10px；1px 细线；**无阴影、无渐变、无光晕**。
- **签名动作（signature move）**：时间轴 = 线路。站点圆点用类别色；同一天多件事 = 大站 + 「换乘」标记；筛选时对应线路变亮、其他变灰，而不是隐藏。
- **禁止**：冷灰 / 蓝色 / 纯黑；卡片套卡片、仪表盘图表、环形进度、连续天数、徽章、暖色渐变、玻璃拟态。

### 1.3 方向契约（开发期约束，不进入交付代码）

**THESIS**：把生活档案做成一张能读的线路图——时间是一条线，经历是站点，同一天多件事是换乘。拒绝卡片瀑布和「生活仪表盘」。

**OWN-WORLD**：暖砂地面、深棕墨、四色线路（训练橄榄 / 吃饭砖红 / 计划赭黄 / 洞察灰褐）、1px 细线、2px 线路、圆点站点、等宽数字。没有冷灰、蓝色与纯黑；没有渐变与阴影。

**STORY**：打开回看先看到一条线；一眼知道这段时间发生了什么、在哪里、多久没练；点站点看到当时的原话与训练明细；从一个站点直接生成下一次安排。

**FIRST VIEWPORT**：390 × 844。顶栏（selfsec · 日期 · 回看 / 安排入口）；标题「回看」；图例一行；线路主体从最近一天的大站开始（训练站带动作 × 组 × 重量，吃饭站带地点与人，计划站带来源），往下是更早的日期；洞察按天折叠成一组。没有底部 tab。

**FORM**：城市导视 / 地铁线路图；seed: 967297543ee3692e（本轮 roll 的 reference；用户选择的 pick 卡 B）。

**FINISH**：unreviewed and undocumented is unfinished; this build ends with the finish review, the verdict, DESIGN.md, and every shipping raster carrying its provenance.

## 2. 信息架构

```
顶栏
├── 回看   全屏视图：线路图时间轴 / 地点 / 搜索
├── 安排   全屏视图：未来 14 天：逾期 / 今天 / 本周 / 更远 / 未定
└── 今天   默认整页聊天：消息流 + composer + 卡片
```

- **不引入常驻底栏。** 回看 / 安排从顶栏入口打开全屏视图，关闭后回到聊天，输入框位置不变。
- 三视图共用同一份数据；视图切换用 hash（`#/today`、`#/recall`、`#/plan`），浏览器返回回到「今天」。
- 回看与安排**只做浏览、勾选、一键生成计划**；要描述的事情回到「今天」输入。
- 详情用全屏 sheet（从底部升起），不是居中 modal；`Esc` / 下滑关闭。
- 回看 / 安排是覆盖层，聊天页的 composer 不参与布局，避免移动端键盘与底栏打架。

### 2.1 今天的聊天框保留什么

保留：顶栏品牌与日期、消息流顺序、气泡、输入框与回车发送、记录卡 / 计划卡 / 洞察卡、合并提示、画像问卷、洞察详情、Token 输入流程。
改变：视觉 token（颜色、圆角、阴影、字体层级）；顶栏「全部」改为「回看」，新增「安排」入口；「待办 / 建立画像」仍在顶栏右侧，不改变功能。聊天区高度与输入框位置保持不变。

## 3. 回看视图

### 3.1 结构

```
顶栏：selfsec · 2026.10.29 · ⌕
标题：回看 / 按日子翻，也按地方找
图例：●训练 ●吃饭 ●计划 ○事件 ○洞察
筛选 chips：最近 / 本月 / 地点 / 训练
────────────────────────────
线路（按天分组，倒序）
  今天 · 10.29            大站
    ◉ 训练 · 胸 · 卧推上到 60
      动作 × 组 × 重量（等宽）
      标签
      同一天换乘 · 吃饭 · 待办
    ○ 吃饭 · 丹粤阁
    ○ 计划 · 周六再去一次
  昨天 · 10.28            大站
    ...
```

- 默认时间轴按 `occurred_on` / `performed_on` 倒序；最近 30 天，滚到底加载更早。
- **洞察默认折叠**：按天合并成一组「洞察 · N 条」，卡面只露第一条标题，点击「展开」才铺开当天全部洞察；筛选「洞察」时不折叠。洞察是外部消息，不应该和自己的生活事件抢同一条线。
- 「地点」chip 切到地点聚合：按 `restaurant_name` / `workouts.place` 分组，显示去过几次、上次哪天、最近一次评价 / 训练。
- 「训练」chip 只看 `domain=workout`。
- 搜索框跨事件正文、经历评价、店名、动作名、计划标题。
- 点站点 → 经历详情 sheet：
  1. **先原话**：`messages(role=me, ref_event_id=...)`，时间戳；
  2. 再结构化：训练动作 / 组 / 重量；吃饭评分 / 同行人 / 菜；计划来源；
  3. 操作：训练「再练一次」、吃饭「再去一次」、计划「改期 / 勾选」。

### 3.2 空状态

没有记录时，线路不画满屏，只留一个起点站：「还没有站点。回去说一句，这里就会长出一条线。」

## 4. 安排视图

```
标题：安排 / 接下来的 14 天
分组：逾期（红）/ 今天（墨）/ 本周（赭黄）/ 更远（灰）/ 想做但没定日期（虚线站）
每个计划 = 一个站点：
  ○ 标题
    日期 · 地点 · 同行人
    来源：来自 10.29 那次吃饭 / 来自一次对话
    [勾选完成] [改到下周]
```

- 逾期项用朱红站点点亮；今天用实心大站；未定日期用虚线圈。
- 完成：`PATCH /api/plans/{id}`；关联了经历的，完成后再问一句「这次怎么样？」，用户说了才落新经历，不自动打分。
- 四种来处：对话直接说、经历卡「再去一次 / 再练一次」、想去地点「安排」、主动问建议（2–3 个有理由的提议，不主动每日推送）。

### 4.1 可选项：安排不是空白页

安排页除了「已经定下日期的计划」，还要能看到「可以选什么」。候选是「想去 / 想做」，没有日期；
点「安排」并选日期之后，才变成计划。

| 分组 | 候选来源 | 能做什么 |
|---|---|---|
| **训练** | `exercises` 动作库（按部位 / 器械筛选） | 选 2–5 个动作 → 组成一次训练 → 选日期生成计划 |
| **美食** | `date_menu` 餐厅（现有 `/date` 菜单） | 选一家 → 选日期生成吃饭计划 |
| **出门玩** | `outing_spots` 种子（景点 / 展馆 / 公园 / 街区 / 活动） | 选一个 → 选日期生成出门计划 |

- 候选卡是**富卡片**：训练显示动作 GIF 缩略图 + 部位 / 器械 / 目标肌群；美食显示封面或色块 +
  菜系 + 距离 / 人均 / 评分 + 推荐理由；出门显示区域 / 类型 / 一句提示。
- 计划点开就是**执行视图**：训练计划按动作顺序展示动画，可直接「完成训练」；美食 / 出门展示店铺 / 地点详情。
  **动画不只在回看里，安排和训练时也能看到。**
- 训练候选支持**多选**（一次训练由多个动作组成）；美食 / 出门一次选一个。
- 每组首屏 6–10 个，可搜索；不做推荐算法排名，不做无限流。
- 计划必须带来源：`ref_type` + `ref_id` 指回动作库 / 菜单 / 出门地点，或 `meta` 里保存动作快照。
- 出门玩的候选先内置一组杭州地点（西湖、灵隐、浙江省博物馆、天目里、良渚、西溪、吴山、南宋御街……），
  表结构与种子分开，之后可在后台增删；聊天里说「想去某地」也应能落成候选（V3.4 再接）。

## 5. 训练日志

### 5.1 数据模型（新增 3 张表）

```
exercises        动作库
  id, name(中文), name_en, body_part(胸/背/肩/腿/手臂/核心/全身),
  equipment(杠铃/哑铃/器械/绳索/自重/其他), target(主要肌群),
  aliases(JSON), source(seed/user), media_url(可空), created_at

workouts         一次训练
  id, user_id, event_id(→events, 可空), performed_on(date), place(可空),
  duration_min(可空), title(如"胸 · 卧推上到 60"), notes,
  source(chat/manual), created_at, updated_at

workout_sets     一组的明细
  id, workout_id, exercise_id(可空), exercise_name(快照),
  set_index(从 1 开始), weight_kg(可空), reps(可空),
  duration_sec(可空，平板支撑等), rpe(可空), is_warmup, note
```

**为什么独立表而不是塞 `events.entities`**：训练需要按动作跨时间查询（「上次卧推多少」「这个月练了几次胸」），
JSON 里的数组做不了干净的聚合。`events` 仍是叙事真相源，训练是它的结构化投影——和 `date_visits` 完全同构。

**去重**：优先按 `event_id` 找已有 workout（同一天合并后的同一事件）；
找不到再按 `user + performed_on + 归一化标题` 兜一层。
补充说明只增不减：空的重量 / 时长不覆盖已有值；`workout_sets` 按 `(exercise_name, set_index)` 覆盖，不重复堆。

**动作匹配**：与 `exercises` 按中文名 / 英文名 / aliases 本地匹配，规则照 `date_visits._match_by_name`。
匹配不到就保留 `exercise_name` 快照、`exercise_id=null`，**不自动新建动作库条目**（避免模型把「哑铃卧推」拆成十条脏数据）。
用户后续可显式补动作。

### 5.2 聊天抽取协议（`services/ai/reply.py` 新增 `workout` 字段）

```json
{
  "workout": {
    "is_workout": true,
    "performed_on": "2026-10-29",
    "title": "胸",
    "place": "城西健身房",
    "duration_min": 42,
    "notes": null,
    "exercises": [
      {"exercise_name": "卧推", "sets": 5, "reps": 5, "weight_kg": 60, "rpe": null, "is_warmup": false},
      {"exercise_name": "哑铃飞鸟", "sets": 4, "reps": 12, "weight_kg": 15, "rpe": null, "is_warmup": false}
    ]
  }
}
```

- 模型只给「动作 + 组数 + 次数 + 重量」的汇总，代码展开成 `workout_sets`（5 组 → 5 行）。
- 判定与回应、事件合并、探店判定仍在**同一次生成**里完成；`route()` 不加调用。
- 未来日期不落训练（当作计划，落 `plans(kind=workout)`）。
- 代码侧只做：`is_workout` 布尔化、日期回退到事件日期、数字范围校验（重量 0–1000、次数 1–100、组数 1–30）、动作名清洗。
- AI 不可用：不建训练记录，事件照记（与探店一致）。

### 5.3 动作库与媒体

- **首期**：内置 80–120 个常见动作（中文名 + 英文名 + 部位 + 器械 + 别名），覆盖胸背腿肩手臂核心。
- **数据来源**：`hasaneyldrm/exercises-dataset` 的元数据（MIT）。动作库元数据随仓库分发。
- **演示动画**：需要，但**媒体不随仓库分发**。
  - 目录 `backend/media/exercises/` 加入 `.gitignore`；部署产物不包含媒体。
  - 从数据集拉取：`python scripts/fetch_exercise_media.py`（默认走镜像，只下载动作库能匹配上的 GIF；已存在文件跳过）。
  - 从自己的目录 / zip 导入：`python -m app.services.fitness_media --source <本地目录 / zip>`。
  - 当前本地已导入 **45 / 54** 个动作，缺失的（bird dog / face pull / 划船机等）保持文字；失败不阻塞训练记录。
  - `exercises.media_path` 存相对路径（如 `exercises/0001.gif`）；前端 `/media/exercises/...` 静态托管，文件不存在时优雅降级为文字。
  - 许可提示写进 `README.md`：exercises-dataset 的元数据是 MIT，媒体版权存在争议；仅允许使用者在本地获取，仓库与部署产物不包含媒体。
- 训练**卡面不显示动画**（保持列表密度）；只在训练详情 sheet 里播放当前动作的演示。
- 种子只补缺失 key，不覆盖用户改过的动作。

### 5.4 统计（纯 SQL，不过 LLM）

- 最近一次某动作：`GET /api/life/workouts/last?exercise=卧推`
- 区间汇总：`GET /api/life/workouts/stats?exercise=&from=&to=` → 次数、最大重量、总容量（重量 × 次数）、训练次数
- 训练卡上的一句比较由本地计算（「比上次 +5kg」），不让模型编数字。

## 6. 生活档案数据层

### 6.1 `services/life.py`（只读投影）

```python
LifeItem = {
  "id", "kind": "event|experience|plan",
  "domain": "workout|dining|general|insight",
  "title", "summary", "occurred_on", "time",
  "place", "people", "tags",
  "ref": {"event_id", "workout_id", "date_visit_id", "plan_id"},
  "raw_messages": [...]   # 原话，详情页用
}
```

- `events(source=user)` → `event`；关联 `workouts` → `experience(workout)`；关联 `date_visits` → `experience(dining)`；
  `plans`（open → 安排，done → 回看）→ `plan`。
- 同一天多条 = 同一天的多个站点；前端画大站 + 换乘。
- 事件详情里的原话来自 `messages(role=me, ref_event_id=...)`，**先原文后摘要**。

### 6.2 新增只读 API

| GET | `/api/life/options?kind=workout\|food\|outing&q=` | 安排页候选池（动作 / 餐厅 / 出门地点） |

| GET | `/api/life/workouts/stats?exercise=&from=&to=` | 训练统计 |

全部走现有 `get_current_user`（`X-API-Token`）。

## 9. 风险与取舍

1. **动作库中文名**：exercises-dataset 是英文元数据，中文名需要首期内置一批 + 模型抽取时保留用户原话。先用高频动作，不追求一次全量。
2. **媒体许可**：不随仓库分发媒体；如需要演示动画，用户本地下载或自托管。
3. **模型抽取训练数据的准确性**：代码只能校验范围与合并，语义仍由模型判断；漏记 / 多记比漏一条事件更可接受，回看里可手工补。
4. **无 Alembic**：`migrate_v4.py` 必须幂等；SQLite 加列用 `ALTER TABLE ADD COLUMN`，MySQL 同。
5. **底部 tab 与输入法**：移动端键盘会改变视口高度，composer 必须用 `visualViewport` 或 `dvh` 处理。
6. **/date 与工作台暂不统一**：本轮只做用户侧三视图；后台视觉下一轮再迁移，避免一次改四个页面导致回归面过大。
7. **视觉世界降级**：impeccable 的 decision page 在本机被权限策略拦截，本轮用本地 HTML 首屏稿 + 结构化选择替代；没有 challenger 质量基准板，方向已经由用户选定，风险已知。

## 10. 已确认的口径（2026-10-29）

1. **导航**：不引入常驻底栏。回看 / 安排从顶栏进入全屏视图；聊天仍是整页，输入框位置不变。
2. **训练粒度**：按「动作 + 组数 + 次数 + 重量」汇总，展示时展开成每组一行；不要求逐组输入。
3. **动作库**：需要演示动画；媒体只在本地获取，不随仓库分发，缺失时优雅降级为文字。
