产品视角：四家各选了哪条路

同样是"记住用户"，四家赌的是完全不同的用户群。ChatGPT 赌消费者要"魔法"，Claude 赌工程师要"可预测"， Hermes 赌"小而常驻比大而检索更好用"，Gemini 赌"结构化和克制"。理解取舍，比记功能表重要。

技术视角：加载 · 初始化 · 迭代

同样一套记忆，差就差在"什么时候进上下文""什么时候被改写""写满了怎么办"。下面三张图回答这三个问题。

2.1 记忆在哪一刻进上下文 时机 × 形态 × 成本

四个时刻：T0 会话开始注入一次 · T1 随每轮请求重发（通常命中前缀缓存）· T2 轮内按需，模型自己发起工具调用 · T3 轮前 prefetch，harness 替模型召回。

记忆块进上下文的时机形态常驻成本对 prefix cache 的影响
Hermes MEMORY.md + USER.md T0 一次，注入后冻结 system prompt 静态块 2200 + 1375 字符 ≈ 1300 token 为保 cache 故意冻结：本轮写入立刻落盘，但本轮 prompt 里看不到，下个会话才生效
ChatGPT 四桶 T1 随每轮请求 显式条目 + 合成画像 + 最近约 40 段对话（只有主题和用户侧消息）+ 交互元数据 大，可到数万 token 可命中前缀；但 dreaming 一更新，整块失效
Gemini user_context T1 分节 statement + 每条 rationale / 日期 statement + rationale 使体积翻倍 同上；且 system prompt 里带"默认忽略"的告警
Claude（claude.ai） T2 纯按需 conversation_search（1–10 条）/ recent_chats（时间游标，可按 project 过滤） 常驻 0 无影响
CLAUDE.md（各层级） T0 每次会话，全部拼接 markdown 拼接（不是覆盖，上层不遮蔽下层） 无硬上限；官方明说"越短越常被遵守" —
子目录 CLAUDE.md / .claude/rules/*.md T2 懒加载 规则文件；带 paths: frontmatter 的按路径匹配生效 常驻 0 —
Claude Code Auto Memory T0 只注入索引（MEMORY.md 前 200 行） 索引：每行 ≤150 字符的指针，指向明细文件 ≤200 行 / ~25KB —
Auto Memory 明细文件 T2 读完索引后自己 pull user_role.md / feedback_testing.md / project_auth_rewrite.md… 常驻 0 —
Claude Skills 三级披露 L1 元数据 T0 常驻 · L2 触发读正文 · L3 再按需读附件 name + description / SKILL.md 正文 / forms.md 等附件 常驻 ≈100 token × 技能数 —
Letta core memory blocks T1 钉在窗口 可编辑块，带 label / description / 字符上限 显式分配 模型自改块会打断缓存
Letta archival · Hermes session_search · Mem0 T2 工具调用 向量 / 图 / FTS5 全文 常驻 0 —
Hermes 外部 provider（Supermemory / Hindsight…） T3 轮前 prefetch 召回片段拼进本轮 每轮少量 天然每轮不同
后台整合产物（dreaming / Auto Dream / 画像） 下次会话（或下一轮）才可见 被重写后的记忆状态 不额外增加常驻 更新即打断前缀缓存

2.2 渐进式索引：三级披露真正的收益 Claude Code / Agent Skills

关键不是"省 token"，而是把"哪段记忆相关"的判断从相似度阈值换成模型自己看目录再决定。 代价也随之固定：多一次工具往返的延迟，且索引质量就是整套记忆系统的天花板。

L1 · 元数据（常驻）
技能只暴露 name + description；Auto Memory 只暴露 200 行索引
~100 token / 项
↓ 模型判断"这个技能/这条记忆可能有用"，才去读正文
L2 · 正文（按需）
用 Bash 读 SKILL.md；用 Read 读 user_role.md
用到才付
↓ 正文里指向附件，模型再决定要不要读
L3 · 附件 / 明细（再按需）
forms.md、reference.md、调试细节、示例
用到才付
买到的

常驻成本 = 目录长度，而不是全部记忆。记忆涨到几万条，常驻仍是常数。

付出的

一次额外的工具往返（可见延迟）；索引描述写得不好 = 永远找不到。而且 Claude Code 的实际检索是 grep 字面匹配，没有语义检索 —— 你记得是 "deploy-time port conflicts"，笔记写的是 "docker-compose port mapping"，就找不回来。泄露源码分析

# ~/.claude/projects/<project>/memory/MEMORY.md —— 常驻的只有这个索引（前 200 行）
- [User role](user_role.md)          — Backend engineer, strong Go, new to React
- [Testing rule](feedback_testing.md) — 集成测试不许 mock 数据库，必须打真库
- [Auth rewrite](project_auth_rewrite.md) — 合规驱动，不是技术债
- [Bug tracker](reference_linear.md)  — 流水线 bug 记在 Linear 的 INGEST 项目

# 模型看到 "Auth rewrite" 这一行，才去读那份明细文件；索引之外的内容本轮完全不可见

同一个模式在三处复现：Claude Code 的索引 + 指针、Anthropic Agent Skills 的三级披露、 Anthropic 官方讲的 "just-in-time 上下文"（保留轻量标识符，运行时才加载数据）。 Claude Code 自己就是混合策略：CLAUDE.md 直接塞进去，其余靠 glob / grep 现取。官方 · Anthropic

2.3 记忆什么时候被写、被改写 四个触发时钟

触发机制一共四种，产品们是把它们组合使用，而不是二选一。

CLOCK 1
会话内即时

工作过程中顺手写。写入立刻落库，不等会话结束。

Hermes memory 工具 · Letta /remember · Claude Code Auto Memory 边干边记
CLOCK 2
阈值 + 定时的整理

攒够量才开一次工，避免空跑也避免迟到。整理动作很具体：把"昨天那个 deploy 问题"改成精确日期、把矛盾条目二选一、删掉引用已删文件的条目。

Claude Code Auto Dream：距上次 >24h 且 新增 ≥5 个会话；也可手打 dream 触发
CLOCK 3
事件驱动（被上下文逼出来）

不是按时间，而是按"发生了值得记的事"或"上下文要爆了"。

Letta dreaming：每 N 个 agent step 之后，或 context 被 compaction 时；可选"第二个后台对话复核后再应用"
CLOCK 4
空闲异步

用你的闲置时间（和更便宜的模型）做记忆维护，不阻塞对话。

Hermes background_review（空闲跑，超 1800s 强制）· Letta sleep-time agent · selfsec 夜间重算画像

另外两家口径不同：ChatGPT dreaming 是"后台进程、不定时、阈值未公开"， Gemini 是"新对话累积到一定量后重算，中间的空档用 recent-turns delta 补"。

2.4 初始化与容量：第一份记忆从哪来，写满了怎么办

系统初始化增量写入后台整合 · 触发条件写满了怎么办
ChatGPT 账号级自动，无显式初始化 会话中；旧版 saved memories 需"记住…"强提示 dreaming 后台进程重写记忆状态；阈值未公开（官方只说 "as time passes"） 无公开上限，由 dreaming 决定
Claude（claude.ai） 空白起步，不初始化 无写入 无 —
Claude Code · CLAUDE.md 用户手写 / /init 生成提案后再落地 用户手改（可 @ 引用其他文件） 无 无硬上限，但越长越不被遵守
Claude Code · Auto Memory 会话中自然产生，分四类：user / feedback / project / reference Claude 自己判断值不值得记，写独立 md 并更新索引 Auto Dream：>24h 且 ≥5 个新会话，后台子 agent 做"反思式整理" 索引 200 行 / ~25KB，超了就挤出旧条目（静默消失）
Letta /init：探仓库、必要时问你的工作风格、用 subagent 读历史会话 每轮学习 + /remember 显式教；agent 自己决定这条该放哪个文件再 commit dreaming / sleep-time：每 N 个 agent step 或 compaction 时；可开"复核后再应用" MemFS 是 git 版本化的；/doctor 审计重复与 prompt token 占用
Hermes 首次启动建空文件 agent 用工具 add / replace / remove background_review：辅助模型，空闲时跑，超 1800s 强制跑 不淘汰、直接报错：返回当前全部条目 + "consolidate now… all in this turn"，逼 agent 当场整合再重试；写入前扫注入 / 外泄模式
Gemini 后台生成首份摘要 摘要 + recent-turns delta（没新聊天时为空） 周期性重算 user_context；阈值未公开 无公开上限

2.5 这些设计各自买到了什么 收益与代价一一对应

01常驻有界小核心
零召回失败、零检索延迟、上下文可预测、前缀缓存友好。代价：容量硬顶，必须有人做取舍 —— 而"取舍"这件事 Hermes 交给了模型当场做。
02满仓时报错而不是静默截断
把"淘汰哪条"从黑箱动作变成一次显式、可审计的决策；对 replace 施加同样上限，逼你压缩而不是把条目写长。
03后台合成（dreaming）
上下文成本从 O(历史) 压成 O(1)，还能吸收从未被显式说过的信息。代价：滞后（生成贵→更新慢→越用越旧）、不可解释，必须配"可读摘要 + 逐条纠正"来补偿。
04渐进式索引 / 三级披露
常驻成本 = 目录长度；相关性判断交给模型而不是阈值。代价：多一次工具往返、索引即天花板、grep 无语义就找不到。
05文件系统即记忆
可 diff、可 git 版本化（Letta MemFS）、可迁移、用户能直接读改、agent 能自纠。代价：会膨胀会自相矛盾，需要审计机制；多进程共享会互相污染（Hermes 明确禁止两个 agent 指向同一个 home）。
06冻结快照
prompt 前缀不变 → 缓存命中 → 省钱省延迟。代价：本轮写的东西本轮看不见。这是纯粹的"钱换实时性"。
07时间戳 + 理由（provenance）
治 staleness（"下周去新加坡"会过期）、可审计、删源会话即级联删派生记忆。代价：每条记忆的 token 翻倍。
08"记忆是线索，不是事实"
Claude Code 的系统提示要求：拿真实代码核对记忆后再行动。几乎没有成本，直接降低"照着旧记忆自由发挥"的概率。

2.6 四个能自己复现的例子

CHATGPT · 有记忆 / 无记忆
同一句话，两种答案

"我要用水下 TTL 闪光，该买什么？"

无记忆：给一张通用清单（要 TTL 支持、要触发器、要线材），兼容性留给用户自己查。

有记忆：直接认出 "Sony A1 II + Nauticam NA-A1II + Backscatter MF-3 + Inon Z-330"，给出具体 SKU （BS-TR-SN2），并指出"没有单个触发器能同时给 MF-3 和 Z-330 真 TTL"，建议按实际想用哪个来选。

时间性例子（官方原文口径）："你下周要去新加坡" —— 时间过去后要被主动改写，而不是永远当现状。

CLAUDE · 显式触发的两面
检索原文，而不是提炼结论

好的一面：问 "我们聊过 Chandni Chowk 吗" → conversation_search 返回 9 段相关对话并合成； 问多主题（Michelangelo / Chainflip / Solana）→ 串行发 3 次检索，22 段对话合并成一段回答，每条都附对话链接。

坏的一面：不显式触发就什么都不知道。"上次那个东西呢"这类指代消解完全落空，而且每次都要等工具跑完。

HERMES · 满仓的时候
记忆 2100 / 2200，再 add 一条 250 字符

工具不写入，直接返回 success: false + 当前全部条目 + "consolidate now… then retry this add — all in this turn"。 agent 必须当场合并几条、删掉过期的，再重试 —— 静默丢条这条路被堵死了。

冻结快照的实际体感：本会话里 add 的条目，本轮 system prompt 里没有，下个会话才出现；工具返回值里是实时状态。

GEMINI / LETTA · 初始化的显式入口
"第一条记忆"通常需要一个明确的动作来产生

Letta：/init 让 agent 先探仓库、必要时问你的工作风格、用 subagent 读历史会话，然后建出记忆层级；/remember always use pnpm in this repo 是显式教学。

Gemini：每条记忆带理由 —— 问"你怎么知道这个"能回溯到具体对话和日期；删掉那场源对话，派生记忆一起被清掉。

03

产品设计：画像 + 馆藏

沿用 Part 1 的三个坐标轴来定自己的位置：记忆靠常驻注入而不是检索、画像要分节而不是一段自由文本、 真相必须落在带日期的事件上而不是提炼出的事实上。整个记忆分成两部分 —— 画像回答"你是谁"，馆藏回答"你做过什么、说过什么"。

画像 · Portrait
你是谁
记忆主体
几段话，分 5 节：身份 / 沟通与风格 / 回避项 / 当前进行中 / 结论级洞察
硬上限
1500 字符（≈550 token）——画像越长越不被遵守，而且这份 token 每轮都要付
谁写
从事件原文里提炼（模型），用户可以纠正
进上下文
T0 全量常驻，每一轮都在
可回溯
每节带来源事件 id + 最近更新时间，问"你凭什么知道"能指回原话
对标：GPT 的 User Knowledge Memories / Hermes 的 USER.md。 差别：它俩只做一段自由文本，我们分节 —— 因为各节"半衰期"不同，可以只重算变了的那节。
馆藏 · Library
你做过什么、说过什么
记忆主体
按标签分档的事件原文 + 一张索引卡
三层
索引卡（常驻目录）→ 分档（按标签的档案，含档首摘要）→ 原文（事件，真相源）
谁写
对话里自然产生，标签由 AI 每次生成（沿用现有设计，不做标签字典表）
进上下文
索引卡 T0 常驻；分档与原文 T2 命中才加载
时间性
事件自带 occurred_on / last_at；档首摘要带 built_at，过期可重算
对标：Claude Code Auto Memory 的"索引 + 指针"、Anthropic 的三级披露、图书馆的卡片目录。 差别：我们的原文是"带日期的、会被补充更新的事件"，不是"事实条目"。

3.1 画像分节：按"半衰期"切，而不是按话题切 抄 Gemini 的核心洞察

分节的目的不是好看，而是让"只重算变了的那节"成为可能 —— 否则每天都要重新描写一遍你的人生。

节内容半衰期更新方式
① 身份年龄 · 职业 · 城市 · 在做的事年几乎不重算，用户改了才动
② 沟通与风格结论先行还是铺垫、语气、格式偏好半年用户纠正时更新
③ 回避项雷区、反感的话术与做法半年出现新雷区时追加
④ 当前进行中项目、计划、期限、正在攻的目标周每次画像迭代都重写
⑤ 结论级洞察"他把技术当面试筹码"这类提炼月与其他节一起

3.3 对初版设计的四处修正

初版设计问题改为
对话 → 事件 → 标签摘要 → 画像（链式） 每层都损耗，误差逐层放大；且画像长度会随标签数无限增长 星型：标签摘要只当"导航层"，画像与它都直接读事件原文，不做链条式传递
标签既当检索键，又当聚合键 标签由模型自由生成 → 同义不同名（#水下摄影 / #潜水摄影）→ 按标签定期总结会碎成一地，无法累积 软归一：prompt 注入"已有标签清单"要求优先复用 + 一张别名表（见 4.5）
每天 00:00 无条件重算画像 没有新信息也在重写 → 文字缓慢漂移，用户什么都没说却看到"它对我的理解变了" 加"新增量"阈值 + 变更摘要 + 版本历史（见 4.4 防漂移）
用"本轮标签"加载相关记忆 标签要在模型理解本轮输入之后才产生，而上下文组装在此之前就完成了（用不上本轮标签） 用会话热标签 + 输入的本地关键词匹配来预取（见 4.2）
概念澄清 · 汇总 ≠ 提炼
为什么"把所有标签摘要拼起来放进画像"是错的

汇总（把每个标签的摘要接起来）长度 = 标签数 × 摘要长度，会无限增长；而且它只是"重排过的馆藏"，不回答任何关于人的问题。

提炼（从原文里挑出关于这个人的结论）有字数上限，必须做取舍 —— "他是什么样的人"本来就是一个有损压缩。

所以两级摘要都存在，但只有目录常驻；进画像的是提炼出的结论，不是汇总的摘要。

3.4 为什么不上向量库：索引优先，检索兜底 本层的核心架构主张

这不是"RAG 不行"，而是在这个规模和这个场景下，索引的收益高于向量检索；并且把"什么时候该换"写成了可触发的条件，而不是靠感觉。

维度标签 / 关键词索引（本项目的选择）向量检索 / RAG
命中语义二值、可解释：字面命中就是命中，精确率（precision）可以到 100%，代价是召回率（recall）低给"概率相关的 top-k + 一个不可解释的相似度阈值"，没有"命中 / 未命中"这回事
错召回的代价低 —— 只有真命中的档才会被加载高 —— 记忆场景里把不相关的旧事塞进 prompt，比漏掉更伤（直接污染当轮回应）
依赖与成本零额外模型：纯 SQL 聚合 + 字符串匹配多一个 embedding 模型、多一份成本、多一个不一致源（事件新增或合并后必须重算向量）
规模收益几百到几千条事件，标签聚合 + 关键词命中已经够用价值随规模增长；>1k 事件、或用户提问完全不用标签词（跨标签语义召回）时才真正划算

关键：语义判断被前移到了写入时刻。给事件打标签，本身就是一次"语义归一"；检索时它退化成精确匹配。 所以"没有向量召回率不够"这个问题不是靠向量补，而是靠每条事件在写进来的时候就已经被归好了档 —— 这是这套设计不需要向量库的根本原因。

为什么"索引 + 渐进式加载"现在才成立：模型侧三个变化 —— 上下文变长（装得下目录）、 编排能力变强（能自己判断该读哪一条）、多轮能力变强（能连续往返取用）。 于是"先把简洁的索引放进 prompt，模型挑完再加载详情"从工程 hack 变成主流设计：Anthropic 的 Agent Skills 三级披露、 官方讲的 just-in-time 上下文、Claude Code 的记忆检索直接用 grep 字面匹配、OpenAI 干脆不做检索 —— 四家都在把"相关性判断"从工程侧的相似度阈值，转移到模型自己身上。这不是我们的发明，是我们在跟这个趋势。

但有一处必须说清 · 我们和 Claude 早期路线的差别
"索引在 prompt 里" ≠ "让模型自己想起来去检索"

Claude 最早是"空白起步 + 用户显式调用才检索"，结果产品侧在 2025/10 之后反而给企业版加了常驻记忆文件 —— 说明纯按需检索顶不住，用户不会每次都显式说"回忆一下"。

所以我们的做法是索引常驻、详情按需：目录永远在 prompt 里（模型每轮都看得见"你有什么"），只有正文走渐进式加载。既拿到索引的精确率，又不会因为"没人提问"而漏。

触发条件 · 什么时候必须换向量
先把"不换"的边界写死

① 事件量 >1k 且索引卡压不进 60 行；② 用户提问长期不使用任何已有标签词（跨标签语义召回失效，表现为"它明明知道却想不起来"）；③ 命中档经常超过 3 档装不下。

任一条持续出现，才引入轻量向量检索，而且以混合检索形式加（关键词 / BM25 + 向量，用 RRF 融合排序）：纯向量不用 —— 公开检索基准上强模型的平均 nDCG@10 也只在 50–60 量级，而 BM25 这类关键词路径至今是它的强补充而非替代。

技术设计：初始化 · 拼接 · 迭代

三个问题：第一份记忆从哪来（初始化）、每轮往上下文里放什么（拼接）、什么时候改写记忆（迭代）。

4.1 初始化：10 题问卷 + 一份可审阅提案 冷启动

设计原则：每题必须能直接产出一句画像，否则不收集；允许跳过、退出保存进度； 最后一屏是"我看到的是这样"的可审阅预览，用户点头才落盘（抄 Claude Code /init 的提案机制）。

关于"科学的 MBTI"：MBTI 的重测信度很差（同一个人隔几周重测，四字母常变），学术共识是大五（OCEAN）。 但 MBTI 有个真实的产品优势 —— 用户熟悉、愿意填、自解释性好。折中做法：不问四字母，改成 MBTI 式的情境二选一（第 5、6 题），一样好填，但不承诺一个站不住的结论。

越稳定的块放越前面：画像与索引卡只在迭代时变、近 40 轮只追加，而每轮都会变的检索块（D）放在最末——前缀缓存从头做最长匹配，一个易变块放前面会让它后面的全部内容一起失效。

记忆开销合计

≈3.0–3.7k token（按下面的换算口径）。加上长 system prompt，整体仍在 4–5k。

对比

ChatGPT 的四桶在重度用户身上是上万 token；我们用 ~3k 拿到"画像全量 + 目录全量 + 相关档按需 + 近期对话"。

token 怎么换：按模型官方口径，1 个英文字符 ≈ 0.3 token、1 个中文字符 ≈ 0.6 token。 所以"1500 字符的画像"其实是约 900 token，不是 550 —— 不要拿英文的 4 字符/token 口径去估中文，会少算约 1.5 倍。上面的预算已按中文口径算。

为什么记忆定在这个长度：因为注意力预算是有限资源。上下文越长，模型对其中任一位置的召回精度越低（context rot），而且中段的信息最容易被忽略（lost in the middle）。 所以画像和索引卡都设硬上限、并且都放在最前 —— 宁可少记，也不让记忆稀释注意力。这和同行的经验值也对得上：Hermes 的用户画像 1375 字符、Claude Code 的记忆索引 200 行，都不是随手定的。

命中规则 · 本地算，不引检索模型
怎么决定加载哪 3 档

① 当前输入里字面出现了已知标签名或别名 → 命中

② 会话热集：本会话最近 3 轮出现过、或刚刚在聊的标签 → 命中（关键在这里：此刻在聊的话题，有哪几个档稳定可知，不必等本轮标签算出来）

③ 兜底：按 last_at 取最近 3 档（时间相关性）

每次最多 3 档，每档最多 3 条事件 —— 上限写死，避免某个话痨标签吃掉整个上下文。

两个必须抄的细节 · 都在 Block C（近 40 轮）上
近 40 轮怎么放，差别极大

只取用户侧消息，不带 assistant 回复。回复通常比提问长好几倍，带上就是花 token 买噪声（GPT 就是这么做的）。

每条带时间锚 + 主题，格式 1006T[09:12] 摄影器材： + 消息。没有时间锚的 40 轮混在一起，模型做不了时间推理，"上次说的那件事"就指代不准。

模型给出的结构化决定，必须本地校验
宁可多一条冗余事件，也不让幻觉改写历史

标签、以及"该并进今天哪条事件"，都是模型给出的判断。本地只认候选集合内的 id：merge_event_id 落在当天事件候选里才生效，不通过就按新建处理。

代价很小（最多多一条冗余事件），收益很大（幻觉永远改不动历史）。同一条纪律也用在降级上：模型不可用时走本地兜底回应，用户看不到报错。

4.3 前缀缓存：它决定了 Block 的顺序 本设计最硬的一条工程约束

这不是"优化"，而是架构能成立的前提：agent 每轮都要重发全部上下文，没有前缀缓存的话，成本会随对话轮数近似平方增长（第 n 轮重发 O(n) 的上下文，n 轮累计 O(n²)）。 缓存把"重发"变成"复用"—— 这就是模型厂商愿意做它、也是多轮 agent 在经济上说得通的原因。

问题答案（决定我们怎么排版上下文）
缓存的是什么KV 张量，不是文本。所以命中要求"逐 token 完全一致的前缀" —— 换一个空格、插一个动态时间戳、JSON 字段顺序变一次，都可能整段 miss
存在哪里按成本分层：GPU 显存 → CPU 内存 → 磁盘。DeepSeek 的"上下文硬盘缓存"把缓存落到磁盘，于是跨请求、跨实例都能复用；显存那一层用分块管理
怎么分块与复用工业界两套主流做法：vLLM 的 PagedAttention 把 KV 切成固定大小的 block、用 block table 映射（像操作系统分页），多个请求可共享同一份系统提示的物理块；SGLang 的 RadixAttention 用基数树存前缀，天然支持多请求前缀共享
匹配粒度各家不同：OpenAI 自动缓存 ≥1024 token 的最长前缀、按 128 token 递增命中；Anthropic 需要显式打 cache_control 断点（5 分钟 / 1 小时 TTL）；DeepSeek 全自动，但规则更严 —— 以「缓存前缀单元」为单位，必须完整匹配某个已落盘的单元才命中，不是"任意长度的最长前缀"都会中（落盘时机有三种：请求的用户输入结束位置、模型输出结束位置、检测到的公共前缀，以及长输入按固定 token 间隔截取）
淘汰策略本质是 LRU：资源紧张时先驱逐最近最少使用的前缀。推论 —— 只有稳定复用的热前缀才留得住，每轮都变的内容连被缓存的机会都很少
计费命中比未命中便宜一个量级：DeepSeek 命中价约为未命中的 1/10；OpenAI 官方折扣 50%（新模型更高）；Anthropic 读 0.1x，但写要付 1.25x（5 分钟）或 2x（1 小时）溢价 —— 意味着一段前缀至少要被读第二次才回本
推论 · 缓存直接决定了四个设计动作
把"缓存友好"当硬约束，而不是事后优化

① 易变的块放最末：命中档每轮都变，放最后只废它自己那 ~500 token；放前面会连带废掉对话历史这个大头。

② 常驻块宁可不更新也不要动前缀：画像和索引卡只在迭代时变。Hermes 更极端 —— 会话内直接冻结记忆块（写入立刻落盘，但本轮的 system prompt 不变），就是为了不打断前缀。

③ 近 40 轮不要实现成滑窗：每轮丢掉最旧一条会让整段前缀整体位移，缓存全废；正确做法是会话内只追加、只在上下文压缩时才整体重写。

④ 反直觉的一点：在"写缓存 1.25x / 读 0.1x"这类计费下，每轮都变的前缀不只是不省，还要倒付写入溢价 —— 所以"把什么放进可缓存前缀"本身就是一道成本题。

⑤ 命中档只注入、不落库：追加式对话天然对齐"上一轮的完整 prompt 就是一个已落盘单元"这一条，所以第 n 轮重放历史能整段命中。但如果把命中档写进 messages 表，下一轮历史里就会多出一条每轮都不同的消息，append-only 的对齐被打断，命中要退化成"等系统慢慢学会公共前缀"。所以命中档只在组装时注入，永不落库。

4.4 迭代：三个时钟 + 一把幂等锁 + 防漂移四条

CLOCK 1
档迭代

每 10 条用户消息（全局累计，不是按会话）触发一次。

只重算"这 10 轮里有新增事件的标签"，通常 1–3 个 —— 不是全量重算，否则成本随标签数线性增长
CLOCK 2
画像迭代

新增轮次 ≥20，或（距上次 >24h 且 新增事件 ≥3）。

分节重算，只重写内容变了的节；④ 当前进行中 每次都重算

画像每次重算都是 LLM 生成，是非确定性的

没有"新增量"阈值 → 每天 00:00 都在没有新信息的情况下重写画像 → 文字缓慢漂移，用户什么都没说，却看到"它对我的理解在莫名变化"。

四条补丁：① 加新增量阈值（CLOCK 2 的条件）② 重算时把上一版画像作为输入，要求"只改有依据的部分" ③ 输出变更摘要（+新增 / ~修正 / −删除）并存版本历史，可回滚 ④ 用已有的 messages.kind=nudge 把变更推给用户 —— "我把你的画像更新了：新增了在做的项目 X"。

4.5 标签软归一：让"聚合键"稳下来

标签由模型自由生成是个好设计（不背标签字典表），但"按标签定期总结"需要一个稳定的键。三层防护，全部不需要硬编码枚举：

层做什么频率成本
① 软归一在模型理解本轮输入时，把已有标签清单一并给它（60 个 ≈ 200 token），要求"优先复用已有标签，确实是新话题才新建"每轮≈200 token
② 别名表模型仍会造新标签，tag_aliases(alias → canonical) 记一笔；检索按 canonical 聚合，不合并事件本身按需一次读写
③ 定期归并输入"标签 + 各自条数"，输出合并建议（#水下摄影 + #潜水摄影 → #水下摄影），确认后应用每周 或 标签数 >60一次轻量调用

这不是标签字典表 —— 内容由模型产生、不是硬编码枚举，守住原来"刻意不做标签字典表"的原则。

4.6 评测：怎么证明记忆真的有用 自研项目最容易被问死的地方

记忆的效果不能靠"感觉它记得我"来证明。同行已经把它变成可量化的东西（LoCoMo / LongMemEval / BEAM），我们至少要有一套自己能跑的自评。

指标怎么测目标
① 档命中率 / 精确率离线回放 30 天真实对话，统计"该命中的档有没有命中"（召回）与"命中的档是否真的相关"（精确）精确率 >90%（本方案天然偏高）；召回率先到 60%，低于 50% 才考虑上向量
② 画像遵守率构造 30 条依赖画像的提问（沟通风格 / 回避项 / 当前目标），人工判分回应有没有用对画像>80%，且明显高于"不给画像"的基线
③ 记忆开销与缓存命中率每次请求记录 input token、记忆块占比、前缀缓存命中的 token 数（各家 API 都会回这类字段，正好可以埋点）记忆块占 input 的 <60%；缓存命中率 >70%
④ staleness 率抽检画像里的条目，人工标"是否已过期 / 已被推翻"<10%；超标就收紧迭代阈值
必须同时看的三个维度
只看准确率会被带进坑里

准确率 + 每查询 token + 延迟，必须一起看。业界 benchmark 的评测框架就是这么搭的（BLEU / F1 / LLM-judge 三项指标 + token 消耗 + 延迟）—— 一个"准确率 95% 但每查询要 26k token"的系统在生产上不可用。

参照系：LoCoMo（1540 题，含多跳与时序）、LongMemEval（500 题，含 knowledge update）、BEAM（1M / 10M token 规模）。我们不去打榜，但要知道它们各自测什么，才说得清自己的指标对应哪一类能力。

最低成本的自评 · 每周 30 分钟
先做能跑起来的那部分

离线回放：拿历史事件与对话重放，只跑检索与拼接、不调 LLM，检查"该加载的档有没有被加载" —— 零成本、可以天天跑，能抓住绝大多数回归。

人工抽检：每周随机抽 10 条真实回复，判断"用对了记忆吗 / 用了不该用的记忆吗"，记成两张计数。样本小，但足以发现系统性问题。

4.7 扩展边界：从单用户到多用户 现在不做，但要知道怎么做

当前是有意的单用户单实例：users 表只做外键锚点、单行；定时任务用内置 asyncio 循环、不引分布式锁。这是个人项目的合理简化，但得说得出"如果多用户会怎么改"。

要改的地方怎么改
记忆的作用域所有记忆表加 scope 维度：user_id（跨会话的事实）+ session_id（会话内）+ agent_id（实例相关），检索时按 scope 合并排序 —— 这就是 Mem0 的"多 scope 标签"做法
画像与索引卡画像变成每用户一行（把 memory_profile 的"单行"约束换成按 user_id 唯一）；索引卡按用户分区，60 行上限不变
定时任务从"单循环 + 内存队列"变成"任务表 + 抢占式认领"，job_runs 的唯一键要带上 user_id，避免同一任务被多实例重复跑
隐藏成本（最关键）前缀缓存不再跨用户共享。单用户时整个 system prompt + 画像 + 索引卡是同一个前缀，命中率极高；多用户时每个用户的画像都不同，能共享的只剩系统提示那一部分 —— 所以必须严格分层：稳定的系统提示（可共享、可缓存）在前，用户记忆（每人一份、不可共享）在后。这会同时改变成本结构和 Block 的顺序设计

本稿待验证的三点

① 索引卡的 60 行上限够不够 —— 标签数涨到 100+ 时，是压缩摘要还是分页？
