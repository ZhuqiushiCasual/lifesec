# 采集层技术选型对比（selfsec 消息推送 · 输入侧）

> 状态：设计稿 v1 ｜ 2026-10-25（**已落地**，实现见 `docs/设计-消息推送.md`）
> 范围：**只讨论"怎么把新闻拿到手"**，不讨论变更检测、判定、推送节流（那三层另开文档）。
> 相关：`docs/hermes-新闻任务.md`（历史回调约定）、`hermes/skills/selfsec-news/SKILL.md`（现行执行 skill）、
> `CLAUDE.md`「与 Hermes 的边界」

## 0. 结论

**不做单一方案，做一条五级降级链，默认从最低成本那一级开始，失败才升级。**

| 级别 | 手段 | 定位 |
|---|---|---|
| L0 | RSS / Atom / sitemap / 官方 API | **主路径**，能覆盖的源全走这里 |
| L1 | HTTP 客户端（httpx / requests） | 主路径，站点是服务端渲染的 |
| L1.5 | `curl_cffi`（TLS 指纹伪装） | L1 被 403 时的第一道免费升级 |
| L2 | Playwright（真浏览器渲染） | 内容靠 JS 渲染时的必需项 |
| L3 | Camoufox（反检测浏览器） | 最后一道工事，只给个别硬骨头 |
| L4 | 搜索引擎语法（`site:` / SERP API） | **只做发现，不做采集** |

三句话记住取舍：

1. **`site:` 是发现工具，不是采集工具。** 它给你"有哪些 URL"，不给"正文"，而且不能长期依赖（见 §5.1）。
2. **Playwright 是渲染器，不是反爬工具。** 它能解决"页面要有 JS 才出内容"，解决不了"Cloudflare 拦你"。
3. **Camoufox 不是银弹。** 它能过一些硬站，但代价是每站单独调 + 作者自述有维护断档（§5.3）。

## 1. 先定约束（否则对比没有意义）

| 约束 | 影响 |
|---|---|
| 执行方是 **Hermes cron** | 脚本模式默认超时 **3600s**（`cron.script_timeout_seconds` 可调）；LLM 驱动的任务按 inactivity 预算计，**跑不了长任务** → 采集必须是"一跑就完"的脚本，不能靠 agent 边想边抓 |
| cron 脚本必须放在 `$HERMES_HOME/scripts/` | 代码不放在 selfsec 仓库里 → 脚本只做"调用 + 回写"，真正的爬取逻辑应留在 selfsec 仓库中由脚本 `subprocess` 调用 |
| **cron 脚本不继承 Hermes 的 secrets**（subprocess env 被清洗） | selfsec 的 `API_TOKEN`、代理账号必须由脚本自己从配置文件读，不能指望环境变量被透传 |
| 平台已存在写入口 `POST /api/insights` | 有 `X-API-Token` 鉴权、按 `source_url` 幂等、落 `events(source=hermes)` + `messages(kind=insight)` → **不需要新增表** |
| 生产 ECS 只有 1.6G 内存 | 浏览器方案要考虑并发度 = 1，甚至不放在 ECS 上跑 |
| 每天目标量级：几十~几百条，AI/Agent 领域为主 | 这是**小规模**问题。任何"必须上分布式/向量库"的方案都是过度工程 |
| 推送的质量要求是 **precision 优先** | 采集侧宁可少抓，不要抓来一堆垃圾还得靠 LLM 兜 |

**关键前提修正**：现在是"让 agent 用 anysearch 搜新闻然后总结"（`hermes-新闻任务.md` 里的现方案）。那套跑得通，但它是 **L4 路径 + LLM 抽取**，成本高、结果不可复现、没法追溯"这条新闻当时原文是什么"。本文档要解决的就是这件事。

## 2. 五种方案的技术原理

### L0：RSS / Atom / sitemap / 官方 API —— 这不是爬，是"读对方的推送"

- **原理**：站点按固定 XML schema 输出最新 N 条（标题、链接、时间、摘要）。客户端用 `feedparser` 一解析就是结构化条目。
- **本质区别**：你不在"抓"，你在"收"。**变更检测这一步直接被消灭了** —— `pubDate` 就是对方告诉你的变更时间。
- **能拿到什么**：条目级元数据（够做推送判断）；正文通常只有摘要，需要点进去二次抓。
- **适用**：技术媒体、官方博客、GitHub Releases、arXiv、绝大多数开源项目站点。
- **实测**：`ithome.com/rss/` → 200，`text/xml`，一次拿到 **60 条**。

### L1：HTTP 客户端直取 HTML —— 能用的地方就别用别的

- **原理**：一次 TCP + TLS 握手拿回 HTML，用 CSS 选择器 / readability 类算法抽正文。
- **检测面**（服务端能看到什么）：`User-Agent`、`Accept-*` 头、**TLS 握手指纹（JA3/JA4）**、HTTP/2 帧序、请求频率、IP 信誉。注意：**`requests` 的 TLS 指纹和 Chrome 差异极大**，这是很多站"直接 403 但你用浏览器能打开"的真实原因。
- **实测**：同一批中文新闻站，`sina` / `cls.cn` / `ithome` / `oschina` 全部 200 且正文完整；`huxiu` 直接 **405** 拒绝。

### L1.5：`curl_cffi` —— 用 6MB 换掉 130MB 浏览器

- **原理**：它是 `curl-impersonate` 的 Python 绑定，把整个 HTTPS 客户端栈伪装成真实 Chrome 的形状（TLS 套件顺序、扩展、HTTP/2 设置）。`impersonate="chrome"` 一行参数。
- **实测依据**：一份 2026 年对 7 种反检测方案的横向测试（31 个 Cloudflare 目标 × 3 轮）里，**`curl_cffi` 这个 6.4MB、连 JS 引擎都没有的包，通过数与 130MB 的定制 Chromium 打平**（26/31）；而 `rebrowser-playwright` 的拦截结果与原生 Playwright **完全一致**。
- **说明**：大量所谓"反爬"，拦的是**指纹**而不是"你有没有脑子"。指纹过了，就不需要浏览器。

### L2：Playwright —— 真浏览器，解决"内容要 JS 才出现"

- **原理**：通过 CDP（Chromium）/ Juggler（Firefox）协议驱动真实浏览器，等 JS 执行完再从 DOM 取内容。它是**测试框架**出身，不是反爬框架。
- **能解决**：SPA 空壳（首包 3KB、正文全靠 XHR 拉）、懒加载、需要交互（点"展开全文"）、需要等特定选择器出现。
- **不能解决**：Cloudflare / Akamai 这类主动挑战。它启动时会暴露 `Runtime.enable`、`Target.setAutoAttach` 等 CDP 调用序列，`navigator.webdriver` 也不干净 —— 上面那份测试里，**原生 Playwright 在 31 个目标上几乎全被拦**。
- **成本**：Chromium ~300MB；每个实例常驻内存 300–500MB；单页 2–6s。**在 1.6G 的 ECS 上只能并发 1，而且和 API 抢内存**。
- **实测**：`36kr.com` 首包 25KB / 3 个 script、`jiqizhixin.com` 首包 3.4KB / 0 个 script —— 去标签后正文分别只有 1.5 万和 2770 字符，典型的 SPA 空壳，**必须渲染**。

### L3：Camoufox —— 在 C++ 层改过的 Firefox

- **原理**（作者自述，2026）：不是往页面里注入 JS 打补丁，而是**在 Firefox 的 C++ 实现层**拦截 canvas / WebGL / screen / navigator 等指纹 API；同时 patch 了 Juggler，让 Playwright 拿到的是一份**隔离的副本页面** —— 页面既看不到 Playwright 的注入痕迹，也看不到自己被监听。输入事件走 Firefox 原生 handler，headless 模式也被改成"看起来像有窗口"。
- **指纹策略**：用 BrowserForge 按**真实市场分布**生成（Linux 占 5% 就只 5% 概率伪装成 Linux），追求"内部一致"而不是"最像 Chrome"。
- **代价**：
  - 作者自己在文档里写了 **"有一年维护断档，基础 Firefox 版本老 + 新发现指纹不一致，性能已经下降"**，目前"在积极开发中"。
  - 指纹一致性是个**无底洞**："几千个数据点都要改，而且互不矛盾"—— 反爬厂商会反复测它，找到一个不一致就全线更新。
  - 想真的用起来，通常还要配代理 + geoip + 每站单独调参。
- **定位**：这是**最后一道工事**，不是默认路径。给"必须抓、且没有替代源"的那一两个站用。
- **许可**：MPL-2.0（可商用，改文件需开源）。

### L4：搜索引擎语法（`site:` / SERP API）—— 借别人的索引

- **原理**：`site:example.com 关键词` 不是"让 Google 去抓"，而是在 **Google 已经建好的索引里做前缀过滤**。返回的是历史库存条目，不是实时抓取结果。
- **两条实现路径，差别巨大**：

  | 路径 | 可行性 |
  |---|---|
  | 自己请求 `google.com/search` | **技术 + 条款双输**。违反 Google ToS；必然遇到 CAPTCHA/风控；需要代理池 + 浏览器；返回结构随时改。**实测本机直连失败**（TLS 握手失败 / 15s 超时），DDG 的 html 端点直接被 reset |
  | 有合同的 SERP API（Serper / SerpApi / Brave / Tavily 等） | 可行，稳定，按次计费（千次量级几美元）。**代价**：只给标题+摘要+URL，**正文还得自己二次抓** |
- **官方通道正在关闭**（这点必须知道）：
  - **Google Custom Search JSON API**：**已对新客户关闭**，并宣布 **2027-01-01 停服**。
  - **Bing Search API**：**2025-08-11 已正式退役**，微软把能力收进了 Azure AI Agents 的 "Grounding with Bing Search"。
  - 结论：**"用官方搜索 API 做长期数据源"这条路已经不存在了**，只剩第三方转售 + 自己抓。
- **实测**：`bing.com/search?q=site:36kr.com` 裸 HTTP 请求返回 **200 / 100KB / 10 条 `b_algo` 结果**。技术上可拿，但同样是 ToS 灰区且结构随时变 —— 只能当**调试和补漏**用。

## 3. 对比矩阵

| 维度 | L0 RSS/API | L1 HTTP | L1.5 curl_cffi | L2 Playwright | L3 Camoufox | L4 SERP |
|---|---|---|---|---|---|---|
| **技术原理** | 读对方格式化输出 | 解析 HTML | 伪装 TLS 指纹的 HTTP | 协议驱动真浏览器 | C 层改过的 Firefox | 别人的索引 |
| **拿到什么** | 元数据 + 摘要 | 全文 | 全文 | 渲染后全文 | 渲染后全文 | 标题 + 摘要 + URL |
| **可复用性** | ★★★★★ 一个 feedparser 通吃 | ★★★★ 一站一 selector | ★★★★★ 与 L1 同代码 | ★★★ 同 L1 + 等待策略 | ★★ 每站调指纹/代理 | ★★★★ 但产出弱 |
| **实现复杂度** | 低 | 低 | 低 | 中 | **高** | 中 |
| **单次成本** | ~0 | ~0 | ~0 | 内存 300-500MB | 400-700MB + 代理 | 按次计费 |
| **单条延迟** | 0.2-1s | 0.3-1s | 0.3-1s | 2-6s | 3-10s | 1-3s |
| **能不能过 Cloudflare** | — | 否 | **多数能**（指纹层） | 基本不能 | 部分能 | — |
| **主要失败模式** | 对方停更 / 只给摘要 | 403 / 405 / SPA 空壳 | 对方查 JS 挑战 | 被识别为自动化 | 指纹不一致、维护断档 | 配额、条款、结构变更 |
| **运维负担** | 极低 | 低 | 低 | 中（内存、僵尸进程） | 高 | 中（含账单） |
| **可复现性** | 高 | 高 | 高 | 中（时序噪声） | 低（随机指纹） | 低（结果个性化/漂移） |

## 5. 五个判断（附理由）

### 5.1 `site:` 只能做发现层，不能做采集层

**我的设计考虑到**：采集通道一旦成为推送系统的**主依赖**，它的每一次波动都会变成用户端的"今天没消息"。因此通道必须满足三条：可复现、条款稳定、正文可得。

`site:` 三条全不满足：
- **不可复现**：索引是库存，结果随 Google 的更新漂移；同一个查询今天 20 条明天 8 条，你无法解释"为什么昨天推了今天没推"。
- **条款不稳**：官方 CSE API 已对新客户关闭且 2027 停服；Bing Search API 2025-08 退役。剩下的都是第三方转售，随时涨价/断供。
- **正文不可得**：它只给摘要，正文仍要二次抓 → 你并没有省掉抓取，只是多绕了一圈、多付一份钱。

**因此**：`site:`（走 SERP API）只用在两个地方 —— ① **源发现**（找出"这个领域还有哪些站在写"）；② **补漏**（RSS 挂了、页面改版了，用它确认"这条新闻确实存在"）。它的角色是**雷达**，不是**管道**。

### 5.2 Playwright 是渲染器，不要当反爬工具

**我的设计考虑到**：把"过反爬"和"执行 JS"混为一谈，是采集层最常见的架构错误 —— 因为二者的成本差 5 倍（0.3s vs 6s，0MB vs 400MB），而且升级路径完全不同。

- 需要 **JS 渲染** → Playwright 是正解，无可替代。
- 被 **Cloudflare 拦** → Playwright 基本无效（实测横向对比里原生 Playwright 几乎全拦），正确顺序是 `curl_cffi`（免费）→ 换源 → Camoufox（最后）。

**因此**：`l2_render` 这个能力只对"确认是 SPA 空壳"的源开启，且必须设置在**低并发 + 硬超时（30s）+ 用完即关**。绝不做"所有源都过一遍浏览器"的默认行为 —— 那是拿 400MB 内存换几毫秒的省事。

### 5.3 Camoufox 是最后一道工事，不是默认武器

**我的设计考虑到**：Camoufox 的价值是"能过别人过不去的站"，但它的成本结构是**边际成本递增** —— 第一个站调通很爽，第三个站开始每个都要单独调指纹/代理/等待策略，而且作者自己承认有一年维护断档、指纹一致性是新战场。押注它的维护节奏，等于把推送系统的稳定性外包给一个人的业余时间。

**因此**：只给 ≤2 个"必须抓且无替代"的源开 L3，并且**强制隔离**（独立进程、独立失败计数、挂了不影响主链路）。其余所有源在 L3 之前必须走完 L0→L2 的降级。

### 5.4 RSS/API 优先，本质是把"变更检测"这件事外包给源

**我的设计考虑到**：推送系统真正的复杂度在"判断什么变了"，而不在"把页面拿下来"。RSS 的 `pubDate` / sitemap 的 `lastmod` / API 的 `updated_at` 直接提供了**权威的变更信号**，等于让源替你做了增量检测。

**因此**：源的准入顺序是 **有 RSS/API 的优先接入**，哪怕它的覆盖面比"硬爬"窄。理由很直接 —— 一个每天稳定给 60 条结构化条目的 RSS，价值高于一个每天要跟反爬斗智的 HTML 页面；前者可以做到"零人工维护跑三个月"，后者一次改版就归零。

### 5.5 Hermes 只做编排与判断，不做抓取执行体

**我的设计考虑到**：cron 的 LLM 模式按 inactivity 预算计时，且每次都是全新会话；让 agent"边浏览边抓"会导致三个后果 —— 不可复现（换了模型结果就变）、不可审计（说不清它到底请求了哪些 URL）、成本不可控（抓 50 个页面 = 50 轮工具调用）。

**因此**：
- **抓取 = 确定性脚本**（`no_agent=True`，零 token，输出可 diff）。
- **判断 = LLM**（摘要、impact、重要性打分、相关性判定）—— 这部分天然需要模型。
- **编排 = Hermes cron**（定时、失败告警、每日汇总）。

这也顺带解决了 `hermes-新闻任务.md` 现方案的问题：现在 LLM 既当"搜索引擎"又当"抽取器"，两者都不该它干。

## 6. 推荐架构

### 6.1 一条降级链

```
对一个源（source）：
  L0  feed 存在？      → feedparser 解析 → 得到条目列表（pubDate 即变更信号）
  L1  HTTP 200？       → 选择器抽正文
  L1.5 httpx 403/405？ → curl_cffi(impersonate="chrome") 重试一次
  L2  正文 < 阈值？     → Playwright 渲染（等待指定选择器，硬超时 30s）
  L3  仍被拦？          → Camoufox（仅白名单源，独立进程）
  全部失败              → 记一条 fetch_failed（带 HTTP 码 / 失败级别），不静默丢
```

产出统一成**一种中间格式**，后面所有环节只认这个格式：

```json
{
  "source": "ithome",
  "url": "https://www.ithome.com/0/xxx.htm",
  "title": "...",
  "published_at": "2026-10-25 08:30:00",
  "content": "正文纯文本…",
  "fetch_level": "L0",
  "raw_hash": "sha256:…",
  "fetched_at": "2026-10-25 09:00:12"
}
```

`fetch_level` 和 `raw_hash` 是这套设计的可观测性核心：**每条新闻都要能说清"从哪一级、拿到的什么"**。

### 6.2 源配置（配置驱动 = 灵活）

```yaml
# sources.yaml —— 加一个源 = 加一段配置，不需要改代码
- name: ithome
  url: https://www.ithome.com/rss/
  level: L0                # 声明的起点，运行时按降级链自动升级
  category: tech
  priority: 5
  interval: 60m
- name: 36kr
  url: https://36kr.com/information/technology/
  level: L2                # 实测 SPA 空壳，直接从渲染起步
  wait_for: ".article-item"
  category: tech
  priority: 4
- name: huxiu
  url: https://www.huxiu.com/channel/105.html
  level: L2
  fallback: L3             # 405 拒绝，允许升到反检测浏览器
  max_items: 20
```

**"灵活"就体现在这里**：新增一个源只写配置；某个源失效只改一行 `level`；某个源长期不行就 `enabled: false`，主链路不受影响。

### 6.3 两级 cron（确定性在前，生成在后）

| 阶段 | 形态 | 做什么 | 成本 |
|---|---|---|---|
| **A. 采集** | `no_agent=True` 脚本 | 跑降级链 → 去重 → 写 `raw/YYYY-MM-DD.jsonl` → 有异常才输出（无异常静默） | 0 token |
| **B. 生成** | agent cron，`context_from=A` | 读 raw → 预筛（关键词/源权重）到 ~10-15 条 → 生成 `summary` / `impact` / `importance` → POST 回写 | 一次 LLM 调用 |

理由：
- A 段失败**不应该**让 B 段编内容 —— 所以 A 段用 `{"wakeAgent": false}` 静默，异常才告警。
- B 段是唯一消耗 token 的环节，且输入是**已落盘的 JSON**，可重放、可对比。

### 6.4 回写（复用现有接口，不改表）

```http
POST http://<selfsec>:8000/api/insights
X-API-Token: <token>
{
  "title": "...", "summary": "...", "impact": "...",
  "category": "tech", "topics": ["Agent"],
  "importance": 4,
  "source_url": "https://...",          ← 平台按它幂等
  "source_name": "IT之家",
  "published_at": "2026-10-25 08:30:00",
  "entities": {                          ← 进 events.entities（JSON，无需改表）
    "fetch_level": "L0",
    "raw_hash": "sha256:…",
    "batch_id": "2026-10-25T09:00"
  }
}
```

**建议**：把 `fetch_level` / `raw_hash` / `batch_id` 塞进 `entities` JSON。表结构不动，但排查问题时能回答"这条是渲染来的还是 RSS 来的""同一批采集有没有漏"。

## 7. 成本与复杂度估算

| 方案组合 | 开发量 | 每日运行成本 | 维护频率 | 覆盖面 |
|---|---|---|---|---|
| 全 L4（现状：agent + anysearch） | 低 | 高（token） | 低 | 广但不可复现 |
| **L0+L1+L1.5（推荐主体）** | **中** | **≈0** | **低** | 覆盖 70-80% 源 |
| + L2（按需开启） | 中 | 内存 | 中 | +15% |
| + L3（白名单 1-2 站） | 高 | 内存 + 代理 | 高 | +5% |

验收口径建议：**连续 14 天，A 段成功率 ≥ 90%，且"零产出"的源不超过 2 个**。达不到就不要加源，先修。

## 8. 失败模式与对策

| 失败模式 | 表现 | 对策 |
|---|---|---|
| 源改用 SPA | 首包从 150KB 掉到 <30KB，正文趋零 | **首包大小告警**（<30KB 且正文 <3000 字符 → 自动升 L2 并告警） |
| 反爬升级 | L1 从 200 变 403/405 | 自动降级 L1.5 → 若仍失败，只告警不硬刚 |
| 选择器失效 | 抓到了但正文为空 | 正文长度阈值 + 与上一轮长度对比（骤降 80% 即告警） |
| 静默丢数据 | 进程崩了没人知道 | cron 非零退出必告警；A 段"零产出"要显式报告（不能静默） |
| 重复推送 | 一条新闻多个源转载 | `source_url` 幂等 + 正文 `raw_hash` 去重（跨源） |

## 9. 需要你拍板的三件事

1. **B 段的 LLM 放在哪一侧？**
   - 放 Hermes（按本文档 §6.3）：不改平台，`context_from` 串起来即可；缺点是平台多一个外部依赖。
   - 下沉到平台（复用 `services/ai/client.py` + 现有降级兜底）：更稳，平台已有 `AIUnavailable` 降级机制；缺点是要新增一个 ingest 异步任务。
   - **我的倾向**：先用 Hermes 侧跑通，验证源质量；源稳定后再下沉。

2. **第一批源定哪几个？**
   - 建议：**L0 三个**（ithome RSS、arXiv cs.AI、1-2 个 AI 公司官方博客）**+ L1 两个**（36kr 科技、机器之心）**+ L2 一个**（做一次渲染链路的实战验证）。
   - 为什么不一次上 20 个：源越多，"为什么这条推了那条没推"越难解释；先证明链路对，再扩量。

3. **要不要为"每一条推送保留原文快照"？**
   - 留：可回溯、可复盘（"当时它写的是什么"），但要存正文全文，SQLite/MySQL 体积会长。
   - 不留：只存 URL + 摘要，链接失效就永久丢失。
   - **我的倾向**：**留**，但只留正文纯文本 + 截断到 2000 字符，存 `events.entities` 之外单独字段或独立小表；这是推送系统唯一"事后无法重建"的东西。

## 附：一句话版本（贴在设计文档开头用）

> 采集层不以"突破反爬"为目标，而以**源准入分级 + 成本递进**为第一约束：因为推送系统的价值来自稳定、可解释、长期可维护的信息流，而不是单次抓取成功率。因此我把采集设计成一条 L0→L3 的降级链（RSS/API → HTTP → TLS 指纹 → 渲染 → 反检测浏览器），把搜索引擎语法降级为"发现与补漏"的雷达而非管道；并把抓取（确定性脚本、零 token）与判断（LLM）在架构上分离，使任一环失效都不影响其余环节。
