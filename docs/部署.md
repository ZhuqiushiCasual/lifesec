# 部署（远程服务器）

目标：后端跑在服务器上，手机用浏览器直接访问 `http://<服务器IP>:8000`。

**首次部署 3 条命令，之后更新 1 条。**

---

## 一、首次部署

```bash
# 服务器上（需已装 docker + docker compose plugin）
git clone https://github.com/ZhuqiushiCasual/lifesec.git selfsec
cd selfsec

# ① 必做：创建 backend/.env（git 里没有它，.gitignore 和 .dockerignore 都排除了）
cat > backend/.env <<'EOF'
OPENAI_API_KEY=sk-你的key
API_TOKEN=自己定一个长一点的随机串
EOF

# ② 起服务（首次会构建镜像 + 初始化数据库，约 1-3 分钟）
docker compose up -d --build
```

验证：

```bash
curl http://127.0.0.1:8000/health        # {"status":"ok"}
docker compose logs -f api               # 看到 "内置调度已启动" 即正常
```

## 二、之后更新

```bash
cd selfsec && git pull && docker compose up -d --build
```

> **老库需要一次性升级**：本次之前建的 `selfsec` 库，时间戳列是 `DATETIME`（精度 0，只到秒），
> 跑一次 `docs/alter-datetime6.sql` 升到 `DATETIME(6)`（见第十一节）；
> 另外 v1 → v2 的结构升级（`messages.role`、`events.tags` 等）跑一次 `migrate_v2.py`（见第十二节）。

浏览器打开 `http://<服务器IP>:8000`。

- 页面就是一个聊天窗口：直接说话 → 得到回应 + 卡片

## 四、如果服务器上还跑着旧版（一定要看）

旧版（Life Secretary）的容器名是 `life-secretary-api` / `life-secretary-mysql`，
新版是 `selfsec-api` / `selfsec-mysql` —— 容器名不冲突，**但两边都要占宿主机的 8000 端口**。

所以直接 `docker compose up -d` 会**因为端口被占用而起不来**。正确顺序是先停旧版：

```bash
# 先找到旧栈在哪
docker ps --format '{{.Names}}\t{{.Ports}}'

# 在旧栈的 docker-compose.yml 所在目录里停掉它
docker compose down          # 加 -v 会连旧数据库一起删，自己决定

# 再起新版
cd ~/selfsec && docker compose up -d --build
```

> 旧版的数据在 `life-secretary-mysql` 那个数据卷里，`docker compose down`（不带 `-v`）
> 只是停容器，数据还在，将来想迁移还拿得到。

## 五、三个必须知道的坑

### 1. `backend/.env` 不建，compose 直接起不来

`.env` 被 `.gitignore` 和 `.dockerignore` 双重排除（里面是密钥，本就不该进仓库）。
而 compose 的 `env_file: backend/.env` **指向不存在的文件会直接报错退出**——
这是故意设计成硬失败的，避免它在缺密钥的情况下静默跑起来（那样所有回应都会降级成"记下了。"，你还以为正常）。

### 2. `API_TOKEN` 留空 = 你的聊天记录对全网开放

服务器 8000 端口是公网可达的。`API_TOKEN` 为空时后端**不校验任何请求**，
任何人扫到这个 IP 都能读取你的全部记录和画像。

**所以 `API_TOKEN` 必须设成非空。** 如果还要更稳，建议后面加一层 Nginx + HTTPS + 限流，
现在这样属于"个人自用可接受，但不要长期裸奔"。

### 3. 旧的 `life_secretary` 库不能复用

新架构的表结构与旧库**同名不同结构**（`events` 表字段完全变了），
而 SQLAlchemy 的 `create_all` **只建缺失的表，不会 ALTER 已有表**。

compose 会自己新建一个干净的 `selfsec` 库，所以不会冲突——
但**旧库里的历史记录不会迁过来**。要迁移得单独写脚本（目前没写）。

## 六、常见问题

**改了 compose 里的 MySQL 密码，结果连不上？**
MySQL 的账号密码只在数据卷**首次初始化时**生效。改了 compose 却不删卷，容器里还是旧密码。
解决：`docker compose down -v`（⚠ 会删掉数据库数据，然后重建）

**手机上"添加到主屏幕"不像个 App？**
PWA 三件套（`manifest` / `sw.js` / icons）在本次瘦身中已删除，这是刻意的——
你说过前端先保持简洁 HTML，后面转 App 再换。现在添加主屏幕只会得到一个普通书签。
想恢复成能全屏启动的 PWA，说一声即可（图标在 git 历史里还找得回）。

**要 HTTPS 吗？**
现在没有。浏览器麦克风（将来做语音输入）必须要 HTTPS，PWA 的 service worker 也一样。
这两件事都属于"后面再说"。

## 八、本台服务器（8.136.46.200）的实际情况

**这台机器有自己的约束，用仓库里默认的 `docker-compose.yml` 会出问题：**

| 事实 | 后果 / 对策 |
|---|---|
| 总内存只有 **1.6G**，MySQL 一个容器就占 ~413M | **不要再起第二个 MySQL**，会 OOM。改用 `docker-compose.server.yml`，复用已有的 `mysql-8.0.32` 容器 |
| MySQL 是独立的 `mysql_default` 网络里的 `mysql-8.0.32` | 新 api 用 `networks.mysql_default`（external）加入它，主机名直接写容器名 |
| Docker 镜像源 `docker.xuanyuan.me` 对 `python:3.12-slim` 返回 **403** | 基础镜像已从华为镜像拉到本地并打过标签，现在是本机镜像，不再依赖该源 |
| 容器内 `pip` 走 `pypi.org` 很慢 | 仓库的 `Dockerfile` 已默认走阿里云源（`ARG PIP_INDEX_URL`），compose 传别的源会覆盖它 |

**部署命令（不是默认那个）：**

```bash
cd /workspace/selfsec
docker compose -f docker-compose.server.yml up -d --build
```

**路径**：代码 `/workspace/selfsec`，配置 `/workspace/selfsec/backend/.env`（含 `DATABASE_URL` / `OPENAI_API_KEY` / `API_TOKEN`，权限 600）。
`docker-compose.server.yml` 是服务器专用文件，不在 git 里（不会被 `git pull` 覆盖）。

> **注意**：服务器上的 `backend/Dockerfile` 和 `backend/requirements.txt` 曾经被就地改过（pip 源参数、
> `sqlalchemy[asyncio]`）。这两个修复**现在都已经进仓库了**（requirements 在 `8556ef4`，
> Dockerfile 的源支持在后续提交里），所以 pull 之前先 `git status --short` 看哪些文件是脏的，
> 把已被仓库覆盖的改动 `git checkout -- <file>` 丢掉，再拉。
> **今后不要再就地改这两个文件**——否则每次 pull 都会卡在同一个地方（见第九节第 5 条）。

## 九、踩过的坑（部署相关）

1. **`sqlalchemy` 必须写成 `sqlalchemy[asyncio]`**
   少了这个 extra 就不会装 `greenlet`，而 SQLAlchemy 的 async 引擎在 **import 时**就抛
   `ImportError: ... requires that the Python 'greenlet' library is installed`。
   本地开发环境往往恰好已有 greenlet，所以**只有干净镜像里才会暴露**——容器会无休止重启。
2. **长构建不能挂在 SSH 会话上**
   会话一断（超时、网络抖动），远端 `docker compose build` 会被一起杀掉，且**不留镜像**。
   要么用 `docker compose up -d --build` 配一个不断开的会话，要么让构建脱离会话运行。
3. **`docker exec -i ... mysql -e "..."` 会吃掉外层脚本的 stdin**
   在 `ssh host 'bash -s' <<EOF` 这种"脚本走 stdin"的写法里，带 `-i` 却不带输入重定向的
   `docker exec` 会把**后面还没执行的脚本行**当成自己的输入吃掉，脚本静默截断。
   凡是 `docker exec` 都要显式加 `< /dev/null`。
4. **`docker compose down` 会让应用下线**，改 `.env` / 换镜像 / 调端口前先想好回滚：
   旧栈回滚是 `cd /workspace/lifesec && docker compose up -d`（数据卷未动）。
5. **在服务器上就地改「被 git 跟踪的文件」，`git pull` 会直接中止**
   服务器的工作区改动没提交，而 `git pull`（= fetch + merge）要更新同一个文件时，
   git 宁可中止也不会覆盖你未提交的改动：

   ```
   error: Your local changes to the following files would be overwritten by merge:
   	backend/requirements.txt
   Please commit your changes or stash them before you merge.
   Aborting
   ```

   （如果服务器上把改动 commit 过，就变成 `CONFLICT (content): Merge conflict in ...`。）
   处理：`git diff <file>` 看清改了什么 → 已被仓库覆盖的就 `git checkout -- <file>` → 再 `git pull`。
   ⚠ **别用 `git reset --hard`**：那会把仓库里没有、只有服务器上有的改动一起抹掉
   （曾经的 `backend/Dockerfile` 就是这种情况）。
   原则：**服务器专属的东西只放不被 git 跟踪的文件**（如 `docker-compose.server.yml`），
   需要长期存在就改进仓库，别改服务器的工作区。

## 十一、老库升级：时间戳精度 DATETIME(6)

### 症状

聊天窗口里，**它对我的回应显示在我发的那条消息上面**（时间顺序反了）。

### 原因

一次 `/api/chat` 会先后落两条记录：

```
events   （我说的原话，created_at = t）
messages （它的回应，created_at = t + 几毫秒）
```

`events.created_at` / `messages.created_at` 是 **MySQL 的 `DATETIME`，默认精度是「秒」**，
毫秒被截断掉之后两条记录的时间戳**完全相等**，`ORDER BY` 就分不出先后，
归并结果只能靠实现细节决定——旧实现正好把它们排反了。

线上 `selfsec` 库实测：**每一对对话都是同秒并列**（`SELECT ... INTERSECT ...` 命中 100%）。

### 处理

1. 代码层已经修好（窗口流按 `(created_at, 轮次)` 归并，同秒时用户轮永远在前）——
   即使不做下面的迁移，显示也已经是正确的。
2. 想把根因也去掉（时间戳能区分到微秒、游标翻页不再受同秒影响），在服务器上执行一次：

```bash
# 容器名按实际情况替换（这台机器上是 mysql-8.0.32）
docker exec -i mysql-8.0.32 sh -c 'mysql -u<user> -p"$MYSQL_PASSWORD" selfsec' < docs/alter-datetime6.sql
```

校验：

```sql
SELECT table_name, column_name, datetime_precision FROM information_schema.columns
 WHERE table_schema='selfsec' AND column_name IN ('created_at','recorded_at','updated_at');
-- precision 应该是 6
```

新部署的库不用管——`app/database.py` 里的 `DateTimeMicro` 会直接把列建成 `DATETIME(6)`。
`create_all` 只建缺失的表、不会 ALTER 已有表，所以**老库必须手动跑一次**。

## 十二、老库升级：v1 → v2（窗口表 + 事件合并）

### 症状

新代码起来之后每个 `/api/...` 都 500，日志里是：

```
sqlite3.OperationalError: no such column: role        （或 MySQL 的 Unknown column 'role'）
```

### 原因

v2 改了两件事，都是结构化改动，`create_all` 不会 ALTER 已有表：

- `messages` 多了一列 `role`（me / secretary）——窗口渲染改成只读这一张表
- `events` 多了 `tags` / `occurred_on` / `last_at` / `merged_count`——事件改为「同一天合并」

### 顺序（先迁移，再让它对外服务）

```bash
cd /workspace/selfsec && git pull

# ① 备份（强烈建议，几秒钟的事）
docker exec mysql-8.0.32 sh -c 'mysqldump -u<user> -p"$MYSQL_PASSWORD" selfsec' > ~/selfsec-before-v2.sql

# ② 用**新代码的镜像**跑迁移（run --rm 会覆盖 CMD，只执行迁移脚本）
docker compose -f docker-compose.server.yml build api
docker compose -f docker-compose.server.yml run --rm api python migrate_v2.py

# ③ 起服务
docker compose -f docker-compose.server.yml up -d --build
```

`migrate_v2.py` 是**幂等**的（重复跑会打印"跳过"），会做这些事：

- `messages` 加 `role` 列，旧行标成 `secretary`
- `events` 加 `tags` / `occurred_on` / `last_at` / `merged_count` 并回填
- 把 `events(source=user)` **一条对一条**搬进 `messages(role=me)`（各指自己那条事件），
  历史事件本身不改写、不删除、不合并

> **为什么历史数据不做同一天合并**：v1 里每行是模型当时判定的"一条记录"，
> **哪几条属于同一件事的信息已经丢了**。按天机械合并会把不相干的事揉成一条——
> 线上真实数据就是这样（10-04 的「跑步」+「想念」、10-05 的「想念」+「桌游」）。
> 合并是给**以后**的新输入用的：迁移完的历史事件照样进"今天已有的事件"候选，
> 新消息该并进哪一条由模型判断。想让某条历史事件的表述变好，直接再说一遍那件事即可。

> ⚠ 顺序反了会怎样：先起新代码 = 每个请求 500（缺列）；先跑迁移 = 旧代码把 `role=me` 的消息
> 也当成"它说的"渲染出来（窗口看着怪），直到新代码起来为止。所以按上面 ①②③ 走。
