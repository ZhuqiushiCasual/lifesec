# 设计稿 v2：地点拓扑 —— 把餐厅 / 玩点做成底层能力

> **状态：设计稿，未开发。** 这一版承接 `设计-推荐线.md`，但改了它的骨架：
> 前稿把「推荐线」当成核心对象，这一版把地点之间的**关系**当核心，推荐线降级成上层的一种编排产物。
> 请先 review 第 1 节的判断是否成立、第 14 节需要拍板的几件事，再决定落到哪一步。

## 0. 一句话

底层是一张**地点 + 关系**的图（餐厅、公园、街区、商场都是节点，坐标 / 分类 / 标签是可扩展属性，
地点之间是可重算、可解释的边）；上层是若干**意图查询**和**配方**。
「选了这个餐厅，推荐餐后闲逛地」不是新功能，是同一个查询换了个锚点和意图。

## 1. 我同意你的判断，并且要说清楚前稿错在哪

前稿的核心对象是：

```
推荐线 = 一个玩的地点 + 一家顺路的餐厅 + 一句为什么
```

这等于把「组合」写死在数据层：`outing_lines` 表里 `note_id + restaurant_id` 是它的全部形状。
于是下面这些用法都落不下来：

| 真实场景 | 前稿能不能表达 |
|---|---|
| 我已经定了吃这家，给我几个餐后能走的地方 | 不能，锚点是笔记不是餐厅 |
| 先定了玩点，附近吃什么 | 勉强，但只能反着配一次 |
| 同一天还想加个咖啡 / 看展 | 不能，一条线只有两段 |
| 我人在湖滨，附近有什么 | 不能，没有「当前地点」这个入口 |
| 新属性（营业到几点、要不要门票、雨天行不行、适合两人还是带娃） | 每加一个就加一列，或者塞进 note 文本 |

**根因**：前稿让「组合」承担了知识，而知识本该在节点和边上。
组合是会变的（今天玩+吃、明天吃+走、后天吃+看展），知识不会。

**我因此改了分工**：

- 数据层只回答「**这个地点是什么、和谁有什么关系**」；
- 计算层回答「**以某个地点为中心、按某个意图，谁排前面**」；
- 编排层回答「**这一天怎么排成序**」。

前稿的「配对算法」被拆成两层：配对不再是 note×restaurant 的一对一打分，
而是「锚点 → 一跳邻居 → 按意图打分」这个通用查询。

## 2. 四层结构

```
┌──────────────────────────────────────────────────────────┐
│ 配方层 recipe      line(玩+吃) / stroll(吃+走) / day(多段) │  可变，随时加
├──────────────────────────────────────────────────────────┤
│ 意图层 intent      nearby(anchor, intent) → 候选+理由      │  一个能力，N 个意图
├──────────────────────────────────────────────────────────┤
│ 关系层 edge        walk / co_note / same_mall / same_area  │  可重算 + 人工覆盖
├──────────────────────────────────────────────────────────┤
│ 节点层 place       坐标 · 分类 · 区域 · attrs(JSON)         │  可无限加属性
└──────────────────────────────────────────────────────────┘
```

| 层 | 谁在改 | 改动的代价 |
|---|---|---|
| place | 采集 / 种子 / 人工 | 只影响这一个地点 |
| edge | 脚本重算 / 人工置边 | 只影响这一对 |
| intent | 加一个意图 = 加一段配置 + 一个打分权重 | 不动表、不动上层 |
| recipe | 加一个玩法 = 一个新函数 | 不动底层 |

**这条竖切的意义**：以后加「雨天室内」「带爸妈」「拍照出片」「人均 80 以内」，
都不用碰数据模型——只要这个维度的信息能挂在 `place.attrs` 或边上。

## 3. 节点层：`places` 只做「最小公共面」

### 3.1 为什么不把餐厅表和玩点表合并

`date_menu` 有口味三轴、人均、点菜避坑；`outing_spots` 有耗时、门票、适合季节。
两个领域表的差异字段加起来比共有的多得多，合并成一张宽表的结果是一半列常年为空。

**我因此只抽公共面**：做拓扑需要的维度其实就四个——「在哪（坐标/区域）」「是什么类别」
「有什么标签」「属于哪个更大的地方（商场 / 景区）」。业务差异继续留在各自领域表。

```
places              ← 拓扑只认这张表
  ├── date_menu     place_id → places.id   菜系 / 人均 / 口味三轴 / 避坑
  └── outing_spots  place_id → places.id   耗时 / 门票 / 适合季节
```

- 推荐、邻居、行程全部只读 `places` + `place_edges`；
- 领域表只在这些地方被读：前端卡片渲染、计划落地（`ref_type=date_menu/outing_spot` 保持不动）。
- `plans.ref_type` **不加 `place`**：计划永远指向用户能看见的业务实体，place 是内部索引，
  否则会出现「计划指向一个前端不认识的 id」。

### 3.2 `places` 字段与可扩展性

```sql
places
  id               uuid pk
  canonical_key    varchar unique   -- 规范化名字，防重复（见 3.3）
  name             varchar(120)
  branch           varchar(80)      -- 分店
  category         varchar(16)      -- eat / play / walk / shop / exhibit / park / street
  sub_kind         varchar(32)      -- 景点/展馆/街区/公园/咖啡/面馆…
  area             varchar(40)      -- 行政区，粗粒度兜底
  address          varchar(255)
  lng, lat         double           -- 可空：取不到就不假装有
  geo_precision    varchar(16)      -- exact / mall / street / unknown
  metro_station    varchar(80)
  metro_exit       varchar(16)
  metro_walk_m     int
  parent_place_id  uuid null        -- 商场内的店 → 指向商场节点；景区内景点同理
  attrs            json             -- 可扩展元数据，见第 5 节
  status           varchar(16)      -- active / hidden / merged
  merged_into_id   uuid null
  source, source_ref
```

`attrs` 现在装的东西（以后只加不减、不加列）：

```json
{
  "tags": ["街区", "书店", "咖啡"],
  "indoor": true,
  "open_till": "22:00",
  "duration_min": 90,
  "crowd": "晚上人多",
  "rainy_ok": false,
  "scene": ["两人", "雨天"],
  "walk_grade": "平路",
  "price_level": 2
}
```

### 3.3 去重的三个坑（都会真实发生）

1. **同一家店多分店**：`canonical_key = 规范化(name) + '|' + 规范化(branch)`，不带 branch 的是母店记录，
   分店各自独立节点，靠 `parent_place_id` 挂到母店上。
2. **商场内多店共用一个坐标**：`geo_precision=mall`，并且 `parent_place_id` 指向商场节点。
   距离计算时同商场一律按 2 分钟处理，不用坐标算（否则会得出「相距 0 米」的荒诞结果）。
3. **「西湖」「西溪湿地」这种是面不是点**：`geo_precision=street`，坐标取常用入口，
   边一律按「入口到入口」解释，卡面写「约 10 分钟到湖边」，不写「走到西湖」。

## 4. 关系层：边是拓扑的实体

### 4.1 为什么关系不能塞进 `attrs`

`attrs` 是单向属性（这个地点有什么）。关系是**双向查询 + 要重算 + 要能解释**：

- 「餐后能走哪」要按 `to_place` 反查，JSON 里没有索引；
- 距离随时间变（新增地铁口、店铺搬迁），派生边必须能整批重算；
- 每条边要说清「凭什么」，这是推荐理由的唯一可信来源（模型编不出来）。

### 4.2 `place_edges`

```sql
place_edges
  id            uuid pk
  from_place_id uuid  → places.id
  to_place_id   uuid  → places.id
  rel           varchar(16)   -- walk / co_note / same_mall / same_area / same_metro / sequence
  directed      bool          -- walk 双向；sequence(玩→吃) 有向
  distance_m    int null
  walk_min      int null
  weight        float         -- 0..1，见 4.4
  source        varchar(16)   -- geo / note / manual / visit
  evidence      json          -- {"rule":"walk<=15min","osrm":..."} / {"note_ids":[...]}
  computed_at   datetime
  unique(from_place_id, to_place_id, rel, source)
```

### 4.3 四类来源，生命周期不同

| source | 谁生成 | 重算策略 | 能否被覆盖 |
|---|---|---|---|
| `geo` | 坐标 + 路网/直线系数 | 每次全量重算，先删后插 | 可被 manual 覆盖 |
| `note` | 同一篇笔记里同时出现的地点对 | 随笔记入库增量重算 | 可被 manual 覆盖 |
| `manual` | 我在工作台手动置边 | **永不自动删除** | 最高优先级 |
| `visit` | 历史 `date_visits` / 计划完成 | 每周重算 | 只调权重，不删边 |

重算伪码（这是「元数据能不断拓展」的关键——新维度只加一个 generator，不动表）：

```
for gen in (geo_gen, note_gen, visit_gen):
    delete edges where source = gen.source
    insert gen.build(places, attrs)
manual 边不参与删除
```

### 4.4 权重怎么定（先拍脑袋，后可调，但要可解释）

| 边 | 初始 weight | 依据 |
|---|---|---|
| walk ≤5 min | 1.0 | 直接进入任何候选 |
| walk 5–10 min | 0.8 | |
| walk 10–15 min | 0.5 | 只进「散步」类意图 |
| same_mall | 0.9 | 同商场，几乎零成本 |
| co_note | 0.3 + 0.1×共现次数，上限 0.9 | 「有人把这两个写在一篇里」 |
| same_area | 0.2 | 无坐标时的兜底，仅用于排序不用于展示理由 |

### 4.5 我评估过通用图模型，判定为过度设计

把边泛化成 `(from_type, from_id, to_type, to_id)` 看起来更像「架构」，代价是：

- MySQL 里失去外键，`from_id` 是字符串，索引选择性和约束都没了；
- 「笔记 ↔ 地点」这种跨类型关系，现有 `note.place_id` 外键就够，不需要进通用边表；
- 现在的量级：27 家餐厅 + 12 个玩点 = 39 个节点，全量邻接矩阵 741 对，两次 SQL 就能算完；
- 服务器 1.6G 内存，跑不起也养不起 Neo4j。

**触发条件**（满足任一再泛化，现在不满足）：出现第二种节点类型（人 / 事件 / 物品）需要和地点建边；
或者需要 3 跳以上的路径查询。

## 5. 元数据「不断拓展」的三条规则

1. **新属性 → `place.attrs`**，不动表。只有当它变成高频过滤 / 排序键时才升列
   （例如 `category`、`lng/lat` 已升列，因为每个查询都要用）。
2. **新关系 → `rel` 加一个枚举值 + 一个 generator**，不动表。
3. **新玩法 → intent 或 recipe 加一条配置**，不动底层。

这三条保证了「拓扑可以长」，而且长出来的东西不需要数据迁移。

## 6. 意图层：`nearby(anchor, intent)` 是那个能力

### 6.1 意图表（V1 只上 3 个）

| intent | 候选条件 | 排序偏好 | 文案角度 |
|---|---|---|---|
| `stroll`（餐后走走） | walk ≤15 min 或 same_mall；排除 `eat` | 平路 > 有景 > 室内备选；营业晚的加分 | 「吃完往 X 走 8 分钟，湖边」 |
| `eat`（就近吃） | walk ≤15 min；`category=eat` | 评分 + 人均匹配 + 没去过 | 「出来就能吃 X，不用挪车」 |
| `indoor`（雨天/避暑） | `attrs.indoor = true`，按距离排 | 距离 | 「下雨就换 X，室内」 |

后面加 `coffee`、`photo`、`night`、`family` 都只是新加一行配置。

### 6.2 打分（确定性，可复现，不调模型）

```
score = 0.35*near + 0.25*rel + 0.25*fit + 0.15*personal

near     = 1.0 / 0.8 / 0.5  按步行分钟分档；同商场固定 0.9
rel      = 边的 weight（取最高的一条）
fit      = intent 要求的 attrs 标签命中率（stroll: 散步/街区/公园/书店/湖边）
personal = 去过 +0.2（熟悉） / 跳过 -0.3 / 收藏 +0.3
```

排序稳定：`score desc, distance asc, place.id asc`——同分不会抖。

### 6.3 理由句是拼出来的，不是编出来的

```
「从{anchor.name}走 {walk_min} 分钟到{place.name}，{place.attrs.tags[0]}，{place.attrs.crowd}」
→「从叶马茶楼走 6 分钟到天目里，街区，晚上灯亮起来更好走」
```

数据缺一段就少写一段，**绝不用「离你很近」「环境不错」这种没有信息量的话填空**。

### 6.4 降级链（重要：没有坐标也要能用）

```
有坐标 → walk 边，写「走 6 分钟」
无坐标但有 area → same_area 边，写「同在西湖区」，卡面不写分钟
都没有 → 不进候选
```

前稿的最大问题是「V1 没有坐标就写同区」，但把同区当成推荐的核心依据；这一版把它明确降级为兜底，
并在 UI 上看出差别（有分钟 vs 只有区）。

## 7. 配方层：推荐线只是 `recipe(line)`

```python
Recipe = Callable[[Anchor, Constraints], list[ItineraryStep]]

line(anchor="play",  eat_within=15) -> [play, eat]        # 玩 + 吃
stroll(anchor="eat", walk_within=15) -> [eat, walk]       # 吃 + 走（P1 只做这个的详情式呈现）
day(date, budget, weather) -> [step, step, step]          # P3
```

### 7.1 我决定不落 `outing_lines` 表

前稿的 `outing_lines` 是**派生结果**，要维护重算、隐藏、状态，本质是把内存里的计算结果换成一张表。
这一版：配方每次实时算（39 个点的量，毫秒级），只有两件事落库：

- **安排**：落 `plans`（两条，`ref_type=date_menu/outing_spot`，幂等键 = 配方 id + 日期）；
- **不想去**：落一行轻量反馈 `recipe_feedback(recipe_key, target_id, action, at)`，
  只用于把对应节点/边降权，不复活也不再展示。

**收益**：少一张要跟数据同步的表；**代价**：每次请求都算一遍（可接受），以及「已安排」的线要在
渲染时和 `plans` 对冲一次（一次 SQL）。

### 7.2 `recipe_feedback` 而不是「隐藏线」

前稿把「不想去」记在线上，线重算后 id 就变了，状态很难对齐；记在**节点 + 配方**上，
重算不影响它，而且能同时喂给 `personal` 打分。

## 8. UI：一个地点浮层 + 意图标签

### 8.1 现在的入口问题

`date` 页、安排页、`#experience` 浮层各自长各自的卡片，同一件事（这个地点周围有什么）
要在三个地方各写一遍。这一版收敛成一个组件：

```
┌ 天目里 ────────────────────────── × ┐
│ [封面] 西湖区 · 街区 · 小红书        │
│ 书店、咖啡和建筑本身都值得逛         │
│                                     │
│ [饭后走走] [就近吃] [雨天]           │  ← intent 标签，默认第一个
│ ─────────────────────────────────── │
│ · 叶马茶楼      走 6 分钟 · 江浙菜   │
│   从这儿走 6 分钟到，晚上灯亮起来…   │
│ · 中国美院象山  走 12 分钟 · 校园    │
│                                     │
│ [安排这一天]                         │
└─────────────────────────────────────┘
```

- 复用现有 `#experience` 浮层（`app.js` 里已有 `/api/life/experiences/{kind}/{id}` 的加载逻辑）；
- **餐厅详情里默认展示 `stroll`**，玩点详情里默认 `eat`——同一组件，默认意图不同；
- 安排页顶部的「推荐线」保留，作为 `recipe(line)` 的产物，卡片可下钻到上面这个浮层。

### 8.2 不做

- 不做地图 / 导航跳转（没有坐标就不做假精确，有坐标也不做，V1 用文字够了）
- 不做月历
- 不在卡片里写「离你很近」这类无信息文案
- 不把笔记里的店自动塞进 `/date` 菜单（菜单仍人工维护）

## 9. API

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/places/{place_id}/nearby?intent=stroll&limit=5` | **核心能力**：锚点 + 意图 → 候选 + 理由 + 走法 |
| GET | `/api/places/{place_id}` | 地点详情（含领域字段 + 父子关系） |
| GET | `/api/places?q=&category=` | 搜索 / 补数据排查 |
| POST | `/api/ingest/places` | 批量 upsert（采集 / 种子 / 回填脚本共用，按 `canonical_key` 幂等） |
| POST | `/api/places/edges` | 人工置边（工作台，`source=manual`） |
| POST | `/api/recipes/line` | 算安排页的推荐线（不落库） |
| POST | `/api/recipes/{recipe_key}/plan` | 落计划（幂等：同一 recipe_key + 目标 + 日期只建一次） |
| POST | `/api/ingest/outing-notes` | 笔记入库（沿用前稿），只作为 `attrs` / `co_note` 边的来源 |

`/api/life/options?kind=food|outing` 保持不变，前端不用改调用方式。

## 10. 坐标从哪来（拓扑的硬前提）

| 方案 | 优点 | 代价 | 我的选择 |
|---|---|---|---|
| 高德 / 腾讯 POI API | 国内准，有门店级坐标 + 营业时间 | 要注册 key，有调用配额 | 准了再说，V1 不用 |
| OSM Nominatim + OSRM | 免费、无 key，`maps` skill 已有封装 | 门店级精度一般，杭州小馆子可能查不到 | **V1 用它** |
| 人工补 | 最准 | 39 个点要手动，但一次就够 | 兜底 |

`geo_precision` 必须如实标：查不到就 `unknown`，宁可少一条边，不要伪造距离。
补坐标是一次性脚本 `scripts/geo_backfill.py`，结果写回 `places`，可重跑（幂等）。

## 11. 迁移顺序（不破坏现有功能）

```
1. 建 places / place_edges / recipe_feedback（纯新增）
2. 回填脚本：date_menu → places、outing_spots → places（写 place_id，不删不改原表）
3. 坐标补全（可分批，缺的不影响启动）
4. 派生 geo 边（幂等重算）
5. 新 API 上线，前端 `#experience` 加一段 nearby（老接口零改动）
6. smoke_test 增补
```

每一步都可单独回滚，第 2 步之前老代码完全不知道 places 存在。

## 12. 分阶段

### P1：地点图谱 + 餐后走走（可验证的最小闭环）

- `places` / `place_edges` + 回填 + 坐标（39 个点）
- `nearby(intent=stroll|eat)` + 确定性打分 + 理由句
- 餐厅详情浮层加「饭后走走」，玩点详情加「就近吃」
- smoke test：至少断言「叶马茶楼 → 天目里」这条边的存在与顺序稳定

### P2：配方抽象 + 推荐线回归

- `recipe(line)` 重写安排页「这周去哪」，复用 P1 的 nearby，不再有 `outing_lines` 表
- `co_note` 边（笔记同现）
- 工作台人工置边（覆盖错配）

## 13. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 坐标不准 | OSM 查不到小馆子，或落到路口 | `geo_precision` 如实标注；人工补；宁可降级为同区 |
| 39 个点太少，图没有意义 | 边长不够，推荐同质化 | P1 就把节点补到 60+（从现有笔记/收藏里提），接受「小而准」 |
| 过度抽象 | 为了「拓扑」造了一堆用不上的概念 | 明确 YAGNI 边界（4.5），只在 P1 用得到的字段上建表 |
| 派生边和人工边打架 | 重算覆盖了手工修正 | `source` 分离 + manual 永不删；重算只删自己那类 |
| 推荐理由变成套话 | 模板拼出来没信息量 | 缺字段就少写；写不出具体信息就不展示这条 |
| 采集合规 | 抓小红书 / 抖音 | 同前稿：个人登录态、低频、不绕风控、不二次分发 |

## 14. 需要你拍板

1. **坐标口径**：V1 用 OSM 免费（省事、小馆子可能查不到），还是现在就去注册高德 key（准、要多一步配置）？
2. **餐后半径**：默认步行 15 分钟，还是收紧到 10 分钟（候选会明显变少，39 个点撑不住）？
3. **P1 方向**：先做「餐厅 → 闲逛」，还是「玩点 → 就近吃」先做（你日常更常从哪一头开始）？
4. **推荐线怎么处理**：P1 先只做地点浮层（安排页不动），还是同时把安排页推荐线切到新配方？
5. **节点要不要扩**：现在 27 家餐厅 + 12 个玩点，P1 是否顺手补到 60+（不然图很稀）？

## 15. 与前稿的差异

| 项 | 前稿 | 这一版 | 原因 |
|---|---|---|---|
| 核心对象 | 推荐线（note + restaurant） | place + edge | 组合会变，知识不变 |
| 配对 | note×restaurant 一对一打分 | nearby(anchor, intent) | 任意锚点、任意方向 |
| 派生结果 | `outing_lines` 表 | 不落库，实时算 | 少一张同步表 |
| 用户反馈 | 存在线上 | 存在节点 + 配方上 | 重算不失联 |
| 元数据 | 固定列 | `attrs` JSON + 升列规则 | 能长 |
| 无坐标时 | 「同区」当主依据 | 降级为兜底并显式区分 | 不假装精确 |
| 笔记表 | 核心输入 | 只作为 attrs / co_note 的来源 | 内容不等于拓扑 |
