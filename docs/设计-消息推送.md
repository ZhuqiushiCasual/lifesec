# 设计 · 消息推送（采集 → Hermes → 前台）

版本：v1.0 ｜ 日期：2026-10-27 ｜ 对应 PRD：`docs/PRD-v2.md` §5.3 / §5.4

---

## 1. 问题与目标

selfsec 已经有一个聊天窗口：用户说的话被记住、被回应。缺的是**外部消息主动找上门**：

- 用户不需要打开十个站点，窗口里就能看到今天值得知道的 AI / 金融消息；
- 每条消息**一眼有总结、想看有详情、不信能回原文**；
- 后台能看见「定时任务到底跑没跑、哪个源坏了」，而不是靠猜；
- 链路可复现：同一批源、同一套解析器，跑两次结果一致。

**非目标**：不做通用 RSS 阅读器、不做推荐算法、不做多用户、不在 selfsec 进程里跑浏览器集群。

## 2. 总体架构

```
┌──────────────────────── selfsec（控制面 + 数据面）────────────────────────┐
│                                                                          │
│  内置调度 07:10 ──┐                                                       │
│  工作台「立即下发」┼──▶ ingest_tasks(queued) ──push(HMAC webhook)──┐      │
│                   │                              pull(tasks/next)──┼──┐   │
│  工作台 /workbench ◀── ingest_runs / sources / messages            │  │   │
│                                                                     │  │   │
│  前台 / ── messages(kind=insight) + events(source=hermes) ◀─────────┼──┼───┤
└─────────────────────────────────────────────────────────────────────┼──┼───┘
                                                                      │  │
┌──────────────────────── Hermes（执行面）─────────────────────────────┼──┼───┐
│  webhook 接收 / cron 轮询 ──▶ claim ──▶ stage A runner（确定性）      │  │   │
│                                              │                       │  │   │
│                                              ▼                       │  │   │
│                                       中间 JSON（items）             │  │   │
│                                              │                       │  │   │
│                                       stage B LLM 生成               │  │   │
│                                              │                       │  │   │
│                         POST /api/ingest/messages ◀──────────────────┘  │   │
│                         POST /api/ingest/tasks/{id}/finish ◀────────────┘   │
└─────────────────────────────────────────────────────────────────────────────┘
```

**为什么这样切**：

| 决策 | 理由 | 备选与否决原因 |
|---|---|---|
| selfsec 存源配置/任务/运行记录 | 单库、可查询、工作台直接读 | 让 Hermes 自己存 → 两个真相源，前台不知道任务是否跑过 |
| 抓取由 Hermes 执行 | 抓取慢、易被限流、可能要浏览器；不能拖垮 API | selfsec 内置爬虫 → 进程耦合、部署变重、失败影响聊天 |
| 抓取脚本仍是仓库代码 | 可版本化、可离线测试、可 review | 让 agent 即兴搜索 → 历史事故：来源随机、不可复现（见 `采集-历史排查-opencode.md`） |
| 复用 `events` + `messages` | 前台/记忆/回溯零改动 | 新建 `insights` 表 → 窗口要跨表归并，已证明会乱序 |
| push + pull 双通道 | push 快；pull 穿 NAT、可自愈 | 只 push → Hermes 在内网时任务永远 queued |

## 3. 数据模型

三张新表，均与记忆层解耦。

### 3.1 `ingest_sources`

一行 = 一个可抓取的站点/接口。**加源 = 加配置，不改代码**。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | str PK | |
| `key` | str unique | 稳定标识（`qbitai`） |
| `name` | str | 展示名（量子位） |
| `home_url` | str | 站点根 |
| `feed_url` | str | RSS / JSON 列表 / Search API 地址，可含 `{limit}` |
| `kind` | str | `rss` / `json_api` / `html` / `github` |
| `level` | str | 期望层级 `L0`–`L3`（记录用） |
| `category` | str | `tech` / `finance` |
| `enabled` | bool | 停用后不进入任务 |
| `priority` | int | 越大越先跑 |
| `max_items` | int | 单次最多条数 |
| `interval_minutes` | int | 预留（当前由每日任务统一触发） |
| `config` | JSON | 选择器、详情模板、查询词等 |
| `last_run_at` / `last_status` / `last_error` | | 工作台健康度 |

### 3.2 `ingest_tasks`

一次「跑一轮」的请求。状态机：

```
queued ──push 成功──▶ dispatched ──claim──▶ running ──finish──▶ succeeded
   │                                              │             ├─ partial
   └──────────── push 失败留在 queued ────────────┘             └─ failed
                                                          任意非终态 ──cancel──▶ cancelled
```

| 字段 | 说明 |
|---|---|
| `id` | `tsk_...` |
| `trigger` | `manual` / `schedule` |
| `status` | 上表 |
| `source_keys` | 空 = 全部启用源 |
| `worker` | Hermes 标识 |
| `dispatched_at` / `started_at` / `finished_at` | 时间线 |
| `error` | 失败摘要 |
| `stats` | `{found, written, merged, ...}` |

### 3.3 `ingest_runs`

任务内**每个源**一行。单源失败不影响其他源，也让工作台能定位「是哪一个源坏了」。

| 字段 | 说明 |
|---|---|
| `task_id` | 外键 |
| `source_key` / `source_name` | |
| `status` | `running` / `succeeded` / `failed` / `skipped` |
| `fetch_level` | 实际用到 L0 / L1 / L1.5 / L2 / L3 |
| `items_found` / `new` / `updated` / `failed` | 条数 |
| `error` | 该源错误 |
| `detail` | `entries` / `rows` / `errors` / `elapsed_ms` |

> `ingest_runs` 与任务收尾的关系：`finish` 时会按 run 的真实结果**再校正一次**任务状态——
> 全部失败 → `failed`，部分失败 → `partial`。防止 Hermes 误报 `succeeded`。

## 4. 源与降级链

### 4.1 首期五个源

| key | 名称 | kind | 列表 | 详情 |
|---|---|---|---|---|
| `jiqizhixin` | 机器之心 | `json_api` | `api/article_library/articles.json?sort=time&page=1&per={limit}` | `api/article_library/articles/{slug}.json` |
| `qbitai` | 量子位 | `rss` | `https://www.qbitai.com/feed` | 文章页 `.content`（L1） |
| `infoq` | InfoQ | `rss` | `https://www.infoq.cn/feed` | 文章页 `.article-content`（L1） |
| `aiera` | 新智元 | `rss` | `https://aiera.com.cn/feed` | WP REST `wp-json/wp/v2/posts/{id}?_embed=1` → `content.rendered`（L0） |
| `github` | GitHub | `github` | Search API | 仓库描述 + stars + topics |

站点适配的坑（已在实现中处理）：

- **量子位**：RSS 摘要常只有标题/一句话，正文页有残缺 `< img`，需要清掉并回退到正文首段；
- **InfoQ**：RSS 摘要经常是「点击查看原文」，`_best_summary` 会改用正文；
- **新智元**：文章页是 JS 壳，但页面自己调 WP REST 取正文；直接走同一接口，比 Playwright 快且稳；
- **GitHub**：`topic:a OR topic:b` 与 `created/stars` 限定组合会返回 0 条，改为每个 topic 单独查后合并；
- **机器之心**：官方 JSON 同时给列表和详情，不需要任何 HTML 解析。

### 4.2 降级阶梯

```
L0   RSS / Atom / sitemap / 官方 JSON API      ← 首选
L1   httpx + BeautifulSoup                     ← 静态 HTML
L1.5 curl_cffi（TLS 指纹伪装）                  ← 简单反爬
L2   Playwright（无头 Chromium）                ← 必须执行 JS
L3   Camoufox（反检测浏览器）                    ← 最后手段
```

原则：

- **能用 L0 就不上浏览器**；浏览器依赖重、慢、在服务器上更容易挂。
- 源配置显式写 `kind` 与 `content_selectors`，降级不是随机试错。
- `allow_render` 控制是否允许 L2；默认关闭，避免一次改版把所有源拖进浏览器。
- 站点改版 → 先改 `config`；长期失效 → 工作台 `enabled=false`，主链路继续跑。

## 5. 任务链路

### 5.1 创建

- **每日调度**：内置 asyncio 循环，到 `INGEST_HOUR:INGEST_MINUTE`（默认 07:10）触发一次；
  用 `job_runs(job="ingest_daily", period_key="day:YYYY-MM-DD")` 做幂等，进程重启不会同一天跑两次。
- **工作台手工**：选源 →「立即下发」；空选 = 全部启用源。

创建即写 `ingest_tasks(status=queued)`，然后尝试 push。

### 5.2 下发（push）

`services/ingest/dispatch.py`：

```http
POST $HERMES_WEBHOOK_URL
Content-Type: application/json
X-Webhook-Timestamp: <unix seconds>
X-Webhook-Signature-V2: hex(HMAC-SHA256(secret, "<timestamp>.<raw body>"))
```

body：

```json
{
  "event": "selfsec.ingest.task",
  "task_id": "tsk_xxx",
  "task": {"id": "tsk_xxx", "status": "dispatched", "source_keys": [], "...": "..."},
  "api_base": "http://selfsec:8000",
  "hint": "调用 /api/ingest/tasks/{task_id}/claim 领取，再按 skill 的流程执行"
}
```

- 成功 → `dispatched`；失败 → **回退到 queued**，记录错误，不重试到死。
- **push 失败不是故障**：pull 通道会把 queued 捡走。这是「最终一定执行」的保证。

### 5.3 领取（pull / claim）

- `GET /api/ingest/tasks/next?worker=hermes`：原子地领最早一个 queued（条件 UPDATE，避免双领）。
- `POST /api/ingest/tasks/{id}/claim`：领指定任务，幂等；已结束 / 被抢返回 `409`。
- 返回任务 + 本次要跑的源配置 + `api_base` + `message_api`，Hermes 不需要再查一次源表。

### 5.4 执行（stage A）

```bash
cd backend
python -m app.ingest.runner --task-id tsk_xxx --out ../.hermes/ingest-tsk_xxx.json
```

runner 的边界：

- **只做确定性工作**：拉列表 → 抽正文 → 日期过滤 → 去重 → 输出 JSON；
- **不调模型、不写消息**；模型只负责 stage B 的总结/详情/影响；
- 每个源结束立刻上报 `POST /tasks/{id}/runs`（成功/失败、层级、条数、耗时、错误）；
- 启动时 `create_all` + 源种子，Hermes 先于 selfsec 启动也不会因缺表崩溃；
- 退出码：至少一个源成功 → 0；全失败 → 1。**退出码不是唯一信号，任务状态以 finish 为准。**

### 5.5 生成（stage B）

Hermes 对中间 JSON 逐条生成：

| 字段 | 约束 |
|---|---|
| `summary` | 1–2 句，≤120 字，只陈述事实 |
| `detail` | 2–5 段，≤1200 字，补充数字/人物/时间线/技术细节 |
| `impact` | 1 句，≤60 字 |
| `topics` | 2–4 个中文名词短语 |
| `importance` | 1–5 |
| `category` | `tech` / `finance` |

硬约束：只能使用 runner 给出的 `content`；正文不足 200 字时 `detail` 可空；无关条目丢弃。
完整提示词与流程见 `hermes/skills/selfsec-news/SKILL.md`。

### 5.6 写回与收尾

1. `POST /api/ingest/messages` 批量写回（幂等）；
2. 可选 `POST /api/ingest/messages/merge` 合并多源同一事件；
3. `POST /api/ingest/tasks/{id}/finish`，带 `status` 与 `stats`；
4. selfsec 按 runs 校正状态，工作台与前台立即可见。

## 6. 消息协议

### 6.1 落库

复用现有结构：

```
events(source=hermes, type=insight, dedup_key=canonical_url)
        │
        └─ messages(role=secretary, kind=insight, card=JSON, ref_event_id=event.id)
```

`card` 里放前台需要的全部字段（标题、总结、详情、影响、来源、时间、原文链接、重要性、标签），
窗口渲染只读 `messages`，不需要再跨表拼。

### 6.2 幂等

`canonical_url` 去掉追踪参数：`utm_*`、`spm`、`from`、`source`、`ref`、`share_*`、`scene`、`click_id`、
排序参数与 fragment。然后：

| 条件 | 行为 |
|---|---|
| `dedup_key` 不存在 | 新建 event + insight message |
| 存在，`raw_hash` 相同 | `skipped`，不重写 |
| 存在，`raw_hash` 不同 | 覆盖内容字段，**保留 status**（已读/隐藏不被打回） |

没有 URL 时退化为 `title` 作为 key；批量中单条失败进 `errors`，不中断整批。

### 6.3 增删改合并

| 操作 | 行为 |
|---|---|
| 新增 / 更新 | 只写 `source=hermes` 的事件与对应 insight 消息 |
| 修改 | 白名单字段；改 `source_url` 会重算 `dedup_key` |
| 删除 | 删 event + 消息；只允许 Hermes 来源 |
| 合并 | `primary_id` 保留并吸收重复项内容，重复项删除；任一 id 不存在则整次 404，不半途生效 |

**永不触碰用户自己记的事件**——这是 Hermes 写接口的硬边界。

### 6.4 前台展示

```
┌────────────────────────────────────────────┐
│ 量子位 · 10月27日 00:06 · 重点              │
│ 刚刚，Anthropic 公开 335 页招股书           │
│ 总结：Anthropic 递交招股书，披露 335 页……   │  ← 卡片上，最多 3 行
│ 影响：AI 公司上市窗口打开……                 │
│ [Anthropic] [IPO]                           │
│ [详情]                    [原文链接 ↗]       │
└────────────────────────────────────────────┘
```

- **总结**：卡片上直接可读，不需要点开；
- **详情**：弹层，分段正文 + 完整元信息；Esc / 点遮罩关闭；
- **原文链接**：卡片和弹层都有，`target=_blank`；
- 回溯抽屉里的洞察条目同样有「详情」「原文链接」；
- 移动端 ≤520px 弹层全屏化。

## 7. 工作台

`/workbench`，原生 HTML/CSS/JS，零依赖。

| 标签 | 内容 |
|---|---|
| 概览 | 任务状态计数、源健康、消息总数/24h/状态/来源、最近任务与 runs、调度与下发配置 |
| 任务 | 选源下发、任务列表、详情（逐源 runs）、重试、取消、手动 dispatch |
| 源 | 增删改、启停、优先级/条数/JSON config、单源立即跑、补回内置源 |
| 消息 | 按源筛选、含隐藏、勾选合并、编辑、隐藏/恢复、删除 |

鉴权：`X-Workbench-Password`；浏览器 `sessionStorage` 保存，关闭标签页即失效。
与 `API_TOKEN`（Hermes 机器凭证）、`X-Date-Password`（约会页）三套独立。

自动刷新 30 秒，弹层打开时暂停。

## 8. 鉴权与安全

| 通道 | 凭证 | 使用者 |
|---|---|---|
| `/api/*`（含 `/api/ingest/*`） | `X-API-Token`（`API_TOKEN`） | Hermes / 脚本 |
| `/api/workbench/*` | `X-Workbench-Password` | 我（浏览器） |
| `/api/date/admin/*` | `X-Date-Password` | 我（约会页后台） |
| `/api/date/menu`、`/api/date/choose` | 无 | 另一半 |

- webhook 用 HMAC V2 + 时间戳，Hermes 侧必须验签与 ±5 分钟窗口；
- 工作台密码为空时**拒绝所有请求**，不默认放行；
- `API_TOKEN` 不进入任何前端静态文件；
- 写消息接口永远不碰 `source=user` 的事件。

## 9. 失败模式与可观测性

| 失败 | 表现 | 自愈 / 处理 |
|---|---|---|
| Hermes 不在线 | 任务停在 queued | pull cron 下次捡走 |
| push 超时 | queued + error | 同上 |
| 单源解析失败 | 该 run failed，其他源继续 | 任务 partial；工作台看 `last_error` |
| 站点改版 | 某源持续 failed | 改源配置或 enabled=false |
| LLM 失败 | 无 summary/detail | 用 runner 原始摘要写回，任务 partial |
| 写回失败 | 消息缺失 | 重试 2 次；已写入的保留；任务 partial |
| 任务卡 running | 工作台可见 | 取消后重试（新建任务） |
| 时间戳精度 | 消息顺序错乱 | 全项目 `DateTimeMicro`（MySQL `DATETIME(6)`） |

可观测性全部落在三张表上：**任务看状态，run 看单源，source 看最近一次**。
工作台是这三张表的只读视图 + 少量写操作。
