## 0. 我这版说法的 review

### 站得住的三条（可以直接讲）

1. **"索引 + 渐进式加载，这就是 skill 的设计"** —— 对。Anthropic Agent Skills 的三级披露就是它：L1 元数据（name + description，约 100 token/skill）常驻 system prompt → L2 `SKILL.md` 正文触发时才用 Bash 读进来 → L3 附件（`forms.md` 之类）正文指到才读。Anthropic 官方还专门写了 just-in-time 上下文：**保留轻量标识符，运行时才加载数据**。
2. **"知识库小的时候索引方式更常用"** —— 对，而且有很硬的佐证：**Claude Code 的记忆检索就是 grep 字面匹配**（泄露源码分析），没有语义检索；它靠的是"索引（`MEMORY.md` 前 200 行）+ 模型读完自己 pull 明细文件"。业界最流行的 coding agent 用的是关键词，不是向量。
3. **"上下文变长、编排变强、多轮变强 → 索引 + 渐进式加载更好用"** —— 方向对。Anthropic 官方原话大意：模型能力变强后，agentic 设计会趋向"让聪明的模型自己行动，人工策展越来越少"。这条本质是 bitter lesson 在上下文工程上的体现。

### 必须改表述的三条（不改会被面试官当场抓）

1. **"关键词命中可以有 100% 的准确率"** → 应该说 **精确率（precision）= 100%**。
   - `precision = TP / (TP + FP)`：命中即相关，没有假阳性 → 100%。
   - `accuracy = (TP + TN) / 总数`：召回率低的时候 accuracy 反而难看，说"准确率 100%"是错的。
   - 正确表述：**"我的方案精确率优先（约 100%），召回率偏低；这是有意的 —— 记忆场景里错召回比漏召回更伤。"**
2. **"语义相似很难做到 90 以上"** → 别说"相似度分数到不了 90"（余弦相似度是 0–1 的值，说"90 分"会被挑）。
   - 准确说法：向量检索的 **recall@k** 在真实长尾数据上很难稳定 90%+；公开检索基准 **BEIR** 上，强模型的平均 **nDCG@10 也只在 50–60 量级**；而且它给的是"top-k + 一个阈值"，**没有"命中 / 未命中"这种二值、可解释的语义**。
   - 补一句更硬的：**BM25 这类关键词路径至今是向量的强补充而不是替代**，混合检索（关键词 + 向量，RRF 融合）常常打败纯向量。
3. **"只调一次 LLM 省成本"** → 站不住。**有前缀缓存时，第二次调用的共享前缀只按约 1/10 计价**，"省钱"这个论据会被打。
   - 真正的理由：① **延迟**（少一次串行往返，用户直接等）；② **这些判断本来就是同一个理解的不同侧面**（意图 / 抽取 / 标签 / 并到哪条事件）。
   - 代价要主动说：**错误会串味**（判定错了，抽取跟着错）、可测性变差、prompt 变长、单点失败。兜底是本地校验（`merge_event_id` 必须在候选集合内）。

### 要主动交代的两个边界（主动说 = 加分，被问到 = 减分）

- **反例**：Claude 产品侧 2025/10 之后反而给企业版加了常驻记忆文件 —— 说明"纯按需检索"在真实产品里顶不住（用户不会每次都显式说"回忆一下"）。
  → 所以我们的设计是 **索引常驻、详情按需**，不是"让模型自己想起来去检索"。反例反而强化了我们的设计。
- **边界**：什么时候必须上向量（三个触发条件，见第 5 节）。把"什么时候该换"写死，比说"我的方案最好"可信得多。

## 1. Token 与成本

- **官方换算（DeepSeek 文档口径）：1 个英文字符 ≈ 0.3 token，1 个中文字符 ≈ 0.6 token。**
  - 心算：中文字数 × 0.6 + 英文单词数 × 1.3 ≈ tokens。
  - **别用英文的"4 字符 ≈ 1 token"去估中文**，会少算约 1.5 倍。我上一版就是这么错的（1500 字符估成 550 token，实际约 900）。
- **输入 / 输出价格差**：输出通常贵 3–4 倍（同样按 token 计）。所以"少生成"比"少输入"更省钱 —— 这也是本项目"每次都只回一句话"在成本上的额外收益。
- **`max_tokens` 与截断**：输出被截断会直接毁掉 JSON 结构（本项目里会毁掉 `merge_event_id` 的返回）。给结构化输出留足额度，或要求模型先输出 JSON 再输出回应。
- **本项目实测口径**：每次 `/api/chat` 的 input ≈ 4–5k（含长 system prompt + 记忆块 ~3k），output 很短（一句话 + JSON）。**待实测填入**。

## 2. 前缀缓存（最该讲透的一块）

**为什么厂商要做：**
- agent 每轮都把全部上下文重发一遍。没有前缀缓存，第 n 轮重发 O(n)、n 轮累计 **O(n²)** —— 多轮 agent 在经济上不成立。**前缀缓存是 agent 架构能成立的前提**，不只是"优化"。
- 对厂商：推理的 prefill 阶段最贵，复用已有 KV 直接省 GPU 时间，还能提高吞吐。所以厂商有动机把它做得越来越自动、越来越便宜。

**缓存到底是什么、存在哪：**
- 缓存的是 **KV 张量，不是文本**。所以命中要求**逐 token 完全一致的前缀**：改一个空格、插一个动态时间戳、JSON 字段顺序变一次，都可能整段 miss。
- 按成本分层存：**GPU 显存 → CPU 内存 → 磁盘**。DeepSeek 的"上下文硬盘缓存"把缓存落盘，于是跨请求、跨实例都能复用。
- 分块与复用（工业界两套主流）：
  - **vLLM 的 PagedAttention**：把 KV 切成固定大小的 block，用 block table 映射（像操作系统虚拟内存分页），多个请求可以共享同一份系统提示的物理块，避免重复占用显存。
  - **SGLang 的 RadixAttention**：用基数树（radix tree）组织前缀，天然支持多请求前缀共享 + LRU 淘汰。
- 匹配粒度（三家不同）：
  - **OpenAI**：自动缓存 **≥1024 token** 的最长前缀，按 **128 token** 递增命中。
  - **Anthropic**：需要显式打 `cache_control` 断点，TTL 5 分钟或 1 小时。
  - **DeepSeek**：全自动，按块匹配，用户无需改代码。
- 淘汰：本质是 **LRU**。推论：**只有稳定复用的热前缀才留得住**。

**计费（决定了什么值得放进可缓存前缀）：**
| 厂商 | 命中折扣 | 备注 |
|---|---|---|
| DeepSeek | 命中价 ≈ 未命中的 **1/10** | 全自动，按块匹配 |
| OpenAI | **50%** 折扣（官方），新模型更高 | ≥1024 token 起、128 递增 |
| Anthropic | **读 0.1x**，但**写 1.25x（5min）/ 2x（1h）** | 有写入溢价 → **前缀至少要被读第二次才回本** |

**四个陷阱（也是我们的四个设计动作）：**
1. 易变的块放前面 → 它一变，后面全部失效。→ **命中档放最末**。
2. 会话中途改写记忆块 → 前缀被打断。→ **常驻块宁可不更新也不要动前缀**（Hermes 直接冻结快照）。
3. 滑动窗口截断 → 每轮丢最旧一条，整段前缀位移。→ **只追加，只在上下文压缩时整体重写**。
4. 每次都变的前缀不只不省，**还要倒付写入溢价**（Anthropic 口径）。

**观测**：各家 API 都会回缓存命中的 token 数（字段名不同），埋点就能算命中率 —— 这正好是本项目 4.6 评测里的指标 ③。

## 3. 长上下文与注意力（解释"记忆为什么这么短"）

- **context rot**（Chroma 2025-07 的研究）：上下文 token 数上升，模型准确召回其中信息的能力下降。不是悬崖，是性能梯度。
- **lost in the middle**（Liu et al. 2023）：关键信息放在长上下文的中段时最容易被忽略 → 开头和结尾是"高注意力区"。
- **Anthropic 的解释（官方）**：上下文是**有限的注意力预算**。注意力是 n² 的成对关系，上下文越长每条关系的"注意力份额"越被摊薄；且模型训练分布里短序列更多，对超长上下文缺乏经验。
- **推论（本项目）**：记忆不是"越多越好"；画像与索引卡设**硬上限**并且放最前。同行经验值：Hermes 用户画像 1375 字符、Claude Code 记忆索引 200 行 / 25KB。
- 另一条推论：**"窗口够大所以不用做记忆分层"是错的** —— 窗口大只解决"装得下"，不解决"注意力被稀释"和"每轮成本"。

## 4. 一次调用 vs 多次调用

- **立场**：意图判定 / 字段抽取 / 标签生成 / 合并判定 = 同一个理解的不同侧面，拆开等于让模型四次重新理解同一句话。
- **支撑**：少 3 次串行往返的延迟；prompt 组装只做一次；上下文只发一次（虽然缓存能摊薄成本）。
- **反方（要能接住）**：可测性差（不好单独评测每一步）、错误串味、prompt 变长导致单点失败、模型既要生成回应又要输出结构化 JSON 容易顾此失彼。
- **我们的兜底**：本地只做能确定的事（`route()` 只判情绪）；`merge_event_id` 必须在候选集合内，否则按新建处理；LLM 失败时本地兜底回应（"记下了。"）。

## 5. 为什么不上向量库 / RAG

**四条论据（按强度排序）：**
1. **语义判断被前移到了写入时刻。** 打标签本身就是一次"语义归一"，检索时退化成精确匹配。所以"没有向量召回率不够"不是靠向量补，而是靠**每条事件写进来时就已经归好档**。← 这是根本原因，也是最容易被记住的一句。
2. **精确率优先是有意的取舍。** 标签 / 关键词命中是二值的、可解释的，精确率约 100%；向量给的是"概率相关的 top-k + 一个不可解释的阈值"。记忆场景里**错召回（把不相关的旧事塞进 prompt）比漏召回更伤**。
3. **规模和成本不划算。** 几百到几千条事件，标签聚合 + 关键词命中已够；引入 embedding 要多一个模型、多一份成本、多一个不一致源（事件新增/合并后必须重算向量，否则索引和真相漂移）。
4. **趋势支持这条路。** 上下文变长 + 编排变强 → "目录进 prompt，模型挑完再加载详情"从 hack 变成主流：Anthropic Agent Skills 三级披露、官方 just-in-time 上下文、Claude Code 用 grep、OpenAI 干脆不做检索。（不是我们的发明，是在跟趋势。）

**边界（写死的触发条件）：** ① 事件量 >1k 且索引卡压不进 60 行；② 用户提问长期不用任何已有标签词；③ 命中档经常超过 3 档装不下。
**届时的做法**：混合检索（关键词 / BM25 + 向量，RRF 融合），**不是纯向量**。

## 6. 评测

- 四个指标：① 档命中率 / 精确率 ② 画像遵守率 ③ 记忆开销与缓存命中率 ④ staleness 率（目标值见 4.6）。
- 两个低成本自评：**离线回放**（只跑检索与拼接、不调 LLM，零成本可天天跑）+ **每周人工抽检 10 条**。
- 业界 benchmark 各自测什么：
  - **LoCoMo**：1540 题，单跳 / 多跳 / 开放域 / 时序记忆。
  - **LongMemEval**：500 题，含**知识更新**（fact 被推翻后能不能改口）、多会话召回。
  - **BEAM**：1M / 10M token 规模，测"扩窗口解决不了的东西"。
- **三件套必须一起看：准确率 + 每查询 token + 延迟。** 一个"准确率 95% 但每查询 26k token"的系统在生产上不可用。

## 7. 工程与扩展

- **幂等（G1）**：定时触发与轮次触发会打架 → `job_runs(job, period_key)` 唯一键，跑过就跳过；不引 APScheduler（符合"内置 asyncio 循环"的极简原则）。
- **存储坑（G3，面试素材）**：
  - MySQL 的 `DATETIME` 默认只到秒，同一秒内落库的多条记录 `ORDER BY` 定不出先后（表现为"它的回应显示在我发送的消息上面"）→ 用 `DATETIME(6)` + Python 侧微秒默认值解决。
  - JSON 字段（`tags` / `entities`）省事但不可索引；需要按标签筛选时要么冗余一张关联表，要么接受全表扫。
  - SQLite / MySQL 双跑：本地零配置，生产 MySQL（`asyncmy`）；注意两边在类型与时间精度上的差异。
- **降级（G2）**：`AIUnavailable` 必须被每个调用方接住并降级，用户永远不该看到报错。
- **多用户（G4）**：加 scope 维度（`user_id` / `session_id` / `agent_id`，Mem0 的做法）；`job_runs` 唯一键加 user_id；**最关键的隐藏成本 —— 前缀缓存不再跨用户共享**：单用户时整个 system prompt + 画像 + 索引卡是同一个前缀，多用户时能共享的只剩系统提示那部分，所以必须"稳定系统提示在前、用户记忆在后"严格分层。

## 8. 速答表（被问到时用）

| 会被问 | 回答要点 |
|---|---|
| 1 个汉字多少 token？ | 约 0.6；英文 1 字符约 0.3。所以 1500 字画像 ≈ 900 token。 |
| 你的记忆层一共花多少 token？ | 约 3–3.7k，占一次请求 input 的大头；其中画像和索引卡各 ~900。 |
| 怎么控制成本？ | 前缀缓存（稳定块在前、易变块在末）+ 只发用户侧历史 + 记忆块设硬上限 + 只回一句话。 |
| 前缀缓存缓存什么？ | KV 张量，不是文本；逐 token 完全一致才命中。 |
| 为什么厂商做前缀缓存？ | 没有它，agent 每轮重发上下文的成本是 O(n²)，多轮 agent 不成立。 |
| 为什么不全塞进 128K 窗口？ | 注意力预算有限、context rot、中间失忆；而且每轮都要为此付钱。 |
| 为什么不上向量库？ | 语义判断前移到写入时刻（打标签）；精确率优先；规模不划算；趋势支持（Skills / grep / just-in-time）。 |
| 语义检索的准度到底怎样？ | recall@k 难稳定 90%+，BEIR 上强模型平均 nDCG@10 约 50–60；且没有命中/未命中的二值语义。 |
| 为什么只调一次 LLM？ | 同一理解的不同侧面 + 少一次串行往返（延迟）。注意别用"省钱"当理由。 |
| 一次调用出错怎么办？ | 本地校验 + 降级：`merge_event_id` 必须在候选集合内，不通过按新建；LLM 挂了走本地兜底回应。 |
| 记忆冲突（旧画像 vs 新事件）怎么办？ | 事件带 `occurred_on` / `last_at`，画像按节重算、带来源事件 id 与版本历史（参考 Gemini 的 rationale）。 |
| 怎么评测记忆效果？ | 四个指标（命中率/遵守率/开销与缓存命中/staleness）+ 离线回放 + 每周抽检；并对齐 LoCoMo / LongMemEval / BEAM 测的类别。 |
| 定时任务和事件触发打架怎么办？ | `job_runs(job, period_key)` 唯一键做幂等仲裁。 |
| 多用户怎么改？ | scope 维度 + job_runs 加 user_id + **注意前缀缓存不再跨用户共享**。 |
