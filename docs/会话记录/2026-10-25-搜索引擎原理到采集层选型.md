## 一句话结论

搜索引擎不是“把所有网站存成快照 + 不停优化排序算法”，而是一台**持续运行的增量变更检测器 + 超大规模倒排索引 + 分层召回排序流水线**。快照从来只是副产品，而且两家早已对外下线；所谓“算法优化”在工业界只占复杂度的一小部分，绝大部分工程量花在抓取调度、索引结构和成本控制上。

而且这件事和你现在的消息推送是**同一个问题**，只是规模差 6 个数量级。第 4 节说这个。

## 一、先纠正三个误解（这三个误解在面试里说出来会被扣分）

**① “抓取所有网站”——抓不全，也不打算抓全。**
Web 没有中央目录（Google 官方文档原话：*there isn't a central registry of all web pages*），URL 只有三个来源：已知页面重访、从已知页面的外链发现新页、站点主动提交 sitemap。每个站点能分到多少抓取配额由“抓取预算”决定，取决于站点规模、更新频率、服务器健康状况（500 错误 = 你慢点）。所以搜索引擎从设计上就在做一个取舍：**覆盖率 vs 新鲜度**，永远选新鲜度优先。

**② “以快照形式自己保存”——对，但快照这个词现在是历史名词了。**
- 百度 2022 年 8 月下线快照，搜狗同期跟进，官方理由是“网页技术发展及代际变迁”——简单说：现代页面大量 JS 动态渲染 + 权限墙，静态快照经常打开就是白屏或变形，还不如让用户直接点原页。
- Google 2023 年底到 2024 年初移除了结果页的 cache 链接（`cache:` 指令后来也废了）。
- **但内部的原文 100% 还存着**。Brin & Page 1998 年的论文里就写得很直白：仓库里保留 *full raw HTML of pages*，还记录每个词的位置信息和字体大小（粗体大字权重更高）。没有原文，就没法重算索引、没法生成摘要片段、没法做现在的 AI 答案溯源（grounding）。

所以准确说法是：**存原文是必须的，对外提供“快照”这个产品形态被淘汰了。**

**③ “优化自己的搜索算法”——分成两件完全不同的事。**

| | 检索 / Retrieval | 排序 / Ranking |
|---|---|---|
| 问题 | 能不能找全（召回） | 找回来的一千条怎么排（精度） |
| 靠什么 | 索引结构 + 工程（倒排、分片、压缩、缓存） | 机器学习（LTR）+ 质量评估 + 反馈数据 |
| 难点 | 规模、延迟、更新 | 标注数据、特征、线上指标 |

搜索引擎的真实流水线：离线链路负责“把网页变成可检索的数据”，在线链路负责“毫秒内从几千亿文档里召回 + 排序”。

## 二、底层到底怎么跑的（五层）

**离线：**

```
URL 发现 → URL Frontier（优先级队列 + 礼貌限速）
   → Fetcher（robots.txt / DNS 缓存 / 反爬对抗 / 渲染 JS）
   → Parser + 正文抽取（去模板、抽标题/时间/作者/链接）
   → 去重（精确 hash + simhash 近似去重）
   → 质量与反作弊（内容农场、镜像站、cloaking）
   → 文本分析（分词/语言识别/实体/链接图计算）
   → 建索引（正排 doc store + 倒排 inverted index）
```

**在线：**

```
Query 理解（纠错、分词、意图分类、改写扩召回）
   → 多路召回（倒排检索 / 向量检索 / 时效通道 / 垂类通道）
   → 粗排（轻模型，几千→几百）
   → 精排（重模型 LTR，几百→几十）
   → 重排（多样性、去重、权威性兜底）
   → 摘要生成（从 doc store 取原文片段）
```

### 2.1 抓取调度：搜索引擎真正的核心算法在这里

抓取不是 BFS 那么简单，Olston & Najork 那篇经典综述（*Web Crawling*, Foundations and Trends in IR, 2010）开篇就说：看着像 BFS，实际上是“管理超大数据结构 + 决定多频繁重访演化中的内容源”两大难题。

调度器是个**双队列**结构：
- **优先级队列**：按页面重要性 × 变更概率排序（首页、新闻页、常更新页优先）
- **礼貌队列**：保证对同一个 host 的并发和频率受控，`Crawl-delay` 只是下限，真实策略更多依赖服务器响应反馈（超时、5xx 就降速）

**重访间隔怎么定？** 这是有理论模型的：把每个页面的变更建模成 **Poisson 过程**，估计它的变更率 λ，然后求解“在总抓取预算约束下最大化整体 freshness”的优化问题——Wolf et al., *Optimal Crawling Strategies for Web Search Engines* (WWW'02) 是最早的形式化，2020 年还有工作在补“在线估计变更率”的算法（arXiv:2004.02167）。

结论很反直觉但很重要：**给高频变更的页面多抓、给万年不动的页面少抓，比“平均用力”整体新鲜度高得多。** 这就是“按变更率分配预算”，不是定时全量爬。

### 2.2 存储：正排 + 倒排，两套索引配合

- **正排（doc store / repository）**：key = 内部 docID，value = 原始 HTML 或清洗后正文 + 元数据（抓取时间、URL、canonical、语言、PageRank 分数）。所有“快照”都是从这渲染出来的。
- **倒排（inverted index）**：key = 词项，value = posting list，每个元素是 `docID + 词频 + 位置列表`。位置列表支撑短语查询（"人工智能 伦理"必须相邻），词频支撑 BM25 打分。

两个关键工程点，值得记住：
- **压缩**：posting list 里 docID 是递增的，所以存 **差值（delta）** 而不是绝对 ID，再配 varint / PForDelta 之类变长编码，压缩比能到 4-10 倍。索引压缩不只是省磁盘，是**省 IO 带宽 → 直接决定 QPS**。
- **分片**：按文档分片（每个分片自带完整局部索引，查询时广播 + 归并）是主流，因为建索引和本地 join 便宜；按词项分片会让一次查询打散到大量机器。

Google 的 Bigtable 论文（2006）里明确说 web indexing 是它的主要 workload 之一，倒排索引就是存在这种宽列存储里的。

### 2.3 排序的四代演进

1. **TF-IDF / BM25**（纯文本统计）：BM25 至今是几乎所有搜索的 baseline，两个修正很关键——词频饱和（一个词出现 100 次不该是 1 次的 100 倍分）+ 文档长度归一化。
2. **链接分析 PageRank**（1998）：把超链接当投票，且投票权重取决于投票者本身的权重。Brin & Page 还提了个常被忽略的点：**锚文本是别人对你的描述**，比页面自己写的标题更可信（防自我吹嘘）。
3. **Learning to Rank**（2005 之后）：把排序变成一个监督学习问题，特征喂 GBDT/NN，用人工标注 + 点击日志训练。这一步之后，“搜索质量”就从算法问题变成数据问题。
4. **语义检索 / 混合检索**（近五年）：双塔 bi-encoder 把 query 和 doc 各自编码成向量，用 HNSW/IVF-PQ 这类 ANN 索引做近似最近邻。它不是替代 BM25，而是**并行跑两路，再融合排序**（RRF 或加权）——因为向量检索擅长语义泛化（"怎么退订" ≈ "取消订阅"），但会丢掉精确匹配（型号、法规编号、人名）。
5. **最新的一步（和你直接相关）**：Bing 在 2026 年 5 月的官方博客里讲，索引的“价值单元”正在从 **document** 变成 **groundable information**——因为 AI 不是“浏览网页的人”，它要的是“能用来作引用、且可溯源的事实”。这是评价函数的根本改变：传统搜索允许排错（用户自己会跳过），AI 答案排错会**在推理链上放大错误**。这句话几乎是给你消息推送量身定的，见第 4 节。

### 2.4 索引怎么更新：Caffeine 是分水岭

2010 年之前，Google 的索引是“分层批处理”，整库刷新要几周，新闻类查询严重滞后。Caffeine 改成了：**把 web 切成小块持续分析、索引持续增量更新**（不是定时全量重建），官方数据是结果新鲜度提升 50%。

工程实现上就是 **base index + delta index** 分层：新文档先写进小的增量索引（内存 + 定期落盘），查询时同时查 base 和 delta 再合并，delta 攒够了后台 merge 进 base。这套思路和 LSM-Tree 同源——**用“写增量 + 后台合并”换“实时可见”**。

### 2.5 去重：不做这个，索引一半是垃圾

转载、镜像、采集站会导致同一个内容出现几千份，重复不仅浪费存储，还会挤占召回名额、拉低排序。做法是两层：
- 精确去重：URL 归一化 + 正文 hash
- **近似去重**：**simhash**（Charikar 的 LSH，Google 的 Manku 等 2007 年论文 *Detecting Near-Duplicates for Web Crawling* 就是干这个的），把文档压成 64 bit 指纹，汉明距离 ≤ 3 就判为近重复。或者 MinHash + LSH 估计 Jaccard 相似度。

## 三、三家的差异（哪些是公开事实，哪些是推测）

**Google**：论文链条最完整——Brin & Page 98（整体架构）、Bigtable 06（存储）、MapReduce 06、Caffeine 10（增量索引）、Percolator、Dremel。它的护城河**不是排序公式，是自研基础设施**：GFS/Colossus、Bigtable、Borg 这些让它能把“抓取和索引解耦”这种架构真的跑起来。外加 Chrome 带来的真实行为数据、以及全网最大的点击反馈闭环。

**Bing**：微软研究院是爬虫理论的重镇——上面那篇 Olston & Najork 综述的作者就是 Yahoo Research + Microsoft Research 的 Najork。Bing 在图像搜索上公开过“级联 + 分片倒排先粗筛、再精排”的工程细节（arXiv:1802.04914）。这几年公开叙事重心转向 grounding。

**百度**：中文场景有真正的特殊问题——分词粒度（"南京市长江大桥"）、简繁/拼音/错别字容错、内容农场与 SEO 对抗、时效性内容（贴吧、知道这类 UGC 的实时性）。生态上它是“搜索 + 自有内容池”的闭环（百科/知道/文库/贴吧），这和 Google 纯索引外部网页的定位不同。

> 面试实操建议：**别背内部系统代号**（什么 Colossus 版本、TeraGoogle 之类），讲“公开论文里的机制 + 为什么这样取舍”永远不会错，讲代号一旦记错就变成硬伤。

## 四、这个和你的消息推送是什么关系（重点）

Olston & Najork 的综述里列了爬虫的四类用途，第四类是：

> **web monitoring services allow their clients to submit standing queries, or triggers, and they continuously crawl the web and notify clients of pages that match those queries.**

**这就是消息推送的定义。** 搜索引擎 = 全网规模的常驻查询变更通知系统；你的推送模块 = 同一套模型的极简版。所以你不是要从零发明，而是要知道**这个问题的完整解空间长什么样，然后砍到你的规模**。

### 该抄的（有理论支撑，且在你规模下成立）

| 搜索引擎机制 | 你的等价物 | 为什么值得抄 |
|---|---|---|
| 按变更率分配重访预算 | 不同信息源用不同轮询间隔，且**从历史变更记录里学出来**，不是固定 5 分钟 | 你只有几十个源，但每天抓几万次全量是纯粹浪费；固定间隔一定会“热的漏、冷的白抓” |
| 双队列（优先级 + 礼貌） | 全局优先级队列 + 每 host 并发/限速 | 保护对方服务，也保护你自己的 IP 不被封 |
| simhash / 内容指纹 | 同一事件被 10 家转载 → 聚合一条推送 | 推送系统最大体验杀手就是重复刷屏，不是漏推 |
| base + delta 增量索引 | 不要每次重算全量评分，只处理新增/变更条 | 与你现有 SQLAlchemy 架构天然兼容 |
| 级联（cascade） | **规则/关键词先粗筛 → LLM 再精判** | 这是省钱的唯一正确姿势，直接决定 token 成本 |
| 召回与精排分离 | 便宜规则负责"别漏"（高 recall），LLM 负责"别错"（高 precision） | 两段目标不同，混在一起做会两头都不好 |

### 不该抄的（在 1~n 个用户、几千条/天的规模下是纯过度工程）

- ❌ PageRank 式链接权威度：你没有全网链接图，用“源白名单 + 作者权威度”就够
- ❌ LTR 训练：你没有点击日志，硬上就是拿规则拟合噪声
- ❌ 向量库/ANN：几千到几十万条，SQL 全文索引甚至 `LIKE` + 关键词打分足够快，引入 pgvector/Milvus 只是给自己加运维债
- ❌ 分布式抓取、索引分片：单机 + 队列就跑得完

### 最关键的差异（这个认知决定你的架构）

传统搜索的隐含假设是 **“宁可多给 10 条，用户自己会跳过”**——排错一条几乎无成本（人自纠错）。推送的假设完全反过来：**推错一条 = 打扰 = 用户信任-1**。

所以你的评价函数和搜索引擎是反的：

- 搜索优化 **recall / nDCG**（找全、排好）
- 推送优化 **precision + 可解释性 + 可撤回**（少推、每条都能说清"为什么推给你"、推错了能撤回/纠偏）

这个思路不是拍脑袋，Bing 那篇 2026 的 grounding 博客讲的就是同一件事：当系统从“指向信息”变成“使用信息”，错误会**在链路上放大**，所以合法输出里必须包含“证据不足时弃权（abstain）”。你的推送必须原生支持**“这条我判断不了，不推”**这个状态——很多推送系统设计时根本没这个分支，结果就是在低置信度上硬推，用户第一天就关掉了。

## 五、结论：真正的难点不在抓取，在这四个决策点

抓取是最容易的部分（`requests` + 定时器）。推送系统真正难的四件事，也是设计阶段该先定下来的：

1. **变更检测的粒度**：整页 hash？正文 hash？还是字段级（价格 / 标题 / 状态）？
   取舍：整页 hash 便宜但噪声大（导航栏、广告一变就触发）；字段级准但每个源都要写抽取器，维护成本线性增长。
2. **“语义变更”的判定**：价格 99→98 该不该推？同一个公告只改了错别字？标题没变但主语换了？
   取舍：纯 diff 一定漏和错，LLM 判定准但贵且慢——这就是 cascade 的用武之地。
3. **多源聚合与节流**：一件事被三个源报道，是一条还是三条？高峰时怎么降级（合并摘要 vs 逐条推）？
4. **幂等与断点回填**：进程重启 / 源挂了两天，恢复后怎么补，且不重复推、不漏推？这需要“抓取游标 + 已处理 watermark + 事件 ID”三元组，是纯粹的数据模型问题。

## 一、实测证据：这是按 User-Agent 分段的准入白名单

LinkedIn 的 robots.txt 开头就明确写了：

```
# LinkedIn may, in its discretion, permit certain automated access to
# certain LinkedIn pages, for the limited purpose of including content
# in approved publicly available search engines.
# If you would like to apply for permission to crawl LinkedIn,
# please email whitelist-crawl@linkedin.com.
```

然后文件里一共 70+ 个 `User-agent` 段，关键的分歧就在这里：

| UA 段 | 规则 | 含义 |
|---|---|---|
| `User-agent: Googlebot` | 只列了 **120 行** 的 `Disallow`（如 `/jobs-guest/`、`/feed/update/`、`/groups/`、`/authwall`、`/learning/me/`） | **默认允许**，只封一小部分 |
| `User-agent: Bingbot` / `baiduspider` / `Yandex` / `360Spider` / `Sogou` | 同样有一套例外清单 | 默认允许 |
| `User-agent: GPTBot` / `ClaudeBot` / `CCBot` / `Bytespider` / `PerplexityBot` | `Disallow: /` | 全封 |
| **`User-agent: *`**（也就是你） | **`Disallow: /`** | **全站禁爬** |

我又实测了两种情况：用 `python-requests` 和用 Chrome 的 UA 去请求一个公开职位页，**都返回 302**（跳转到 authwall 登录页）。robots.txt 忽略规则强行抓取的话，会收到 LinkedIn 自创的 **999 状态码**（Request Denied）。

所以真实的因果关系是：

> 不是因为 Google 技术更强，所以能抓到；而是 LinkedIn 主动允许 Google 抓，所以 Google 才拿得到；反过来，你爬不到，也不是因为技术不行，而是 LinkedIn 的规则不允许。

**而且这还是一笔交易**：LinkedIn 需要从 Google 获取搜索流量来获得新用户和职位曝光，所以愿意开放公开子集给搜索引擎爬取；但它绝不希望自己的数据被某个第三方完整复制，所以对 `*` 全站封禁。**搜索引擎的抓取权限是靠流量交换换来的，不是靠技术突破获得的。**

## 二、五个具体机制，逐条拆

**① 准入发生在网络层，并非内容层**
robots.txt 只是声明的规则，服务器还会做实际校验。Googlebot 的 IP 是公开可查的：从官方 IP 段反向解析出 `*.googlebot.com` / `*.google.com` 到域名，再正向解析回原 IP，这两步都通过了才被信任。你伪造 UA 很容易，但伪造不了 IP 归属，所以 LinkedIn 一眼就能看出“自称 Googlebot 但从某个家宽 IP 来”的是假的。

**② `site:linkedin.com` 命中的，是 LinkedIn 主动开放的那一小部分**
在 Googlebot 被允许抓取的范围内，实际能抓到的包括公开个人主页 `/in/xxx`、公开职位 `/jobs/view/xxx`、Pulse 文章、公司页。被封掉的路径包括：`/feed/update/`（信息流）、`/groups/`（群组）、`/connections*`、`/learning/me/`、`/checkpoint/`。所以你在 Google 上**永远搜不到某人的好友列表、私信、群组讨论**：连搜索引擎都拿不到，这不是你一个人的问题。

**③ 种子（seed）的来源不一样：Google 的起点是全网的外链，并非 LinkedIn 首页**
这是最容易被忽略的一条。你可以试试自己从 `linkedin.com` 首页开始做 BFS：首页就是登录墙，一步都走不出去。
而 Google 发现某个 LinkedIn 个人页，常常是因为这个人在 GitHub、博客、简历网站上留下了指向自己 profile 的链接。**Google 的种子 URL 是全网几万亿个页面的外链图**。这是真正的规模优势：并非算得更快，而是能知道你想不到的那些 URL 存在。
另外，LinkedIn 还给搜索引擎提供了公开页面 sitemap；职位页更是有专门通道：Google 官方推荐职位类页面用 Indexing API 主动推送更新，而且这类页面必须带 `JobPosting` 结构化数据。也就是说，**这些数据是 LinkedIn 主动交给 Google 的**。

**④ 渲染能力：Google 索引的是 JS 执行之后的 DOM**
LinkedIn 的页面外壳是 JS，正文要等客户端渲染才出现。Google 有独立的无头 Chrome 渲染队列，索引的是渲染结果；你用 `requests` 拿到的只是一片骨架。这一项你确实能追平，但成本很高，对你的场景并不值得。

**⑤ 时间维度：你看到的是库存，不是实时**
`site:` 命中的是几个月前抓取入库的条目，所以“搜得到但点开 302 到登录页”是常态。Google 官方文档对 `site:` 的说明也很保守：*已编入索引的网址可以出现，但不保证一定出现*；结果条数只是估算，千万别拿它当作收录量的精确计数。

## 四、对你 selfsec 推送模块的直接推论（这才是重点）

**不要把“对抗反爬”写进设计目标。** 如果你的推送依赖绕过 LinkedIn 的登录墙，这套方案在三个维度上都很脆弱：随时会被封 IP 和账号，随时可能触碰用户协议（ToS）的法律边界，随时会因为对方改版而中断；而且它违反了“可解释”这条原则：你都不好意思跟用户说这条消息是怎么来的。

| 级别 | 定义 | 例子 | 你的策略 |
|---|---|---|---|
| **A 级** | 官方 API、RSS、公开 sitemap、结构化数据 | 官方公众号 RSS、招聘站 API、政府公告页、RSSHub 能覆盖的源 | 首选，稳定，可以做变更检测 |
| **B 级** | robots 允许、无需登录的公开页面 | 大多数新闻站、公司博客、公开职位页 | 可以做，遵守限速 |
| **C 级** | 要求登录，或逐 UA 全封 | LinkedIn、微博、微信、小红书、知乎登录后才可见的内容 | **不在服务器侧硬爬** |

C 级唯一合规的进入方式，是把凭证责任交还给用户：**由用户自己的浏览器或登录态去获取，系统只负责聚合**。这恰好和你 selfsec 的产品定位一致：**它是替你查看信息，而不是替全世界抓取信息**，所以它天然有资格使用“你的身份”。这也是它在“抓不到 LinkedIn”这件事上唯一的结构性优势，比 Google 还强。Google 拿不到登录后的内容，而一个运行在你自己登录态里的个人秘书可以拿到。

## 一、BFS = Breadth-First Search（广度优先搜索）

**它是图遍历的一种策略**，并非某种爬虫专有技术。把网页看成节点、超链接看成有向边，整个 Web 就是一张有向图；BFS 就是“先访问完所有距离种子 1 步的节点，再访问所有 2 步的，依次向外扩展”。

用队列实现（FIFO），对照的 DFS（Depth-First Search，深度优先）用栈。

**一个具体例子**，种子是 `news.example.com`：

```
深度0:  [首页]                     ← 第 1 轮抓
深度1:  栏目A, 栏目B, 关于我们      ← 第 2 轮抓（全是首页直接链出的）
深度2:  文章1, 文章2, 文章3, 招聘   ← 第 3 轮抓
深度3:  文章1的评论页, 相关阅读…    ← 第 4 轮抓
```

DFS 的做法会变成：顺着首页 → 栏目A → 文章1 → 相关阅读 → 那个作者的主页 → 他的另一篇文章…**一路钻到底**，可能几千次请求都在一个角落里，首页其他栏目一个都没抓。

**为什么爬虫偏爱 BFS（三个真实理由）：**

1. **浅层页面通常更重要**。首页、栏目页、详情页在深度 1-3；存档页、日历翻页在深度 20+。BFS 保证预算先花在高价值层。
2. **广度即覆盖**。同一层往往是同类页面，早抓完早发现“原来这个站还有 40 个栏目”。
3. **天然适配预算分配**。可以按深度设配额：深度 1-3 全抓，深度 4-6 抽样，深度 7+ 只抓明显有价值的。

**但真实爬虫不用纯 BFS。** 纯 BFS 有个致命问题：深度 2 可能有 1000 万个 URL，你必须全部抓完才能进深度 3 —— 而其中大部分是垃圾（tag 页、日历页、无限分页）。所以工业界用的是 **best-first / 优先级 BFS**：`URL Frontier` 是个优先队列，排序键大致是

```
优先级 ≈ 页面重要性 × 预估变更率 ÷ 抓取成本
```

也就是上一条讲的抓取调度。**BFS 提供“发现顺序的骨架”，优先级队列决定“实际抓取顺序”**，两者是配合关系。

另外两个和 BFS 绑定的工程细节：
- **visited 集合**：BFS 必须去重，否则无限循环。几亿 URL 存不下 → 用 **Bloom filter**（布隆过滤器，Brin & Page 1998 年的论文里明确用了它做 URL 去重，可接受的假阳性会漏掉少量页面，但省下几个数量级的内存）
- **复杂度** O(V+E)，时间和“抓取配额”正相关，所以 BFS 的成本就是你愿意付的请求数

## 二、robots.txt = Robots Exclusion Protocol（爬虫排除协议）

**全称是 Robots Exclusion Protocol，简称 REP。** 它是一部写在网站根目录下的纯文本文件，告诉爬虫“哪些路径你可以抓，哪些不可以”。

**历史**：1994 年由 Martijn Koster 提出，一直是事实标准，**2022 年 9 月正式成为 IETF 标准 RFC 9309**（Standards Track，作者包括 Google 的 Gary Illyes、Henning Zeller）。这是我刚才从 rfc-editor.org 拉的原文，不是二手资料。

### 必知的 5 条规则

**① 位置是硬性的，只有一个合法位置**

```
https://example.com/robots.txt      ✅ 只有这个
https://example.com/blog/robots.txt ❌ 无效，爬虫根本不看
```

必须是 scheme + host + port 的根路径。子目录放一个完全没用（很多人踩这个坑）。

**② 语法只有四样东西**

| 指令 | 含义 | 例子 |
|---|---|---|
| `User-agent` | 这条规则对谁生效，`*` 表示所有 | `User-agent: Googlebot` |
| `Disallow` | 禁止抓的路径前缀 | `Disallow: /admin/` |
| `Allow` | 例外放行（用于覆盖上面的 Disallow） | `Allow: /admin/public/` |
| `Sitemap` | 反向声明：站点地图在哪（这是“请来抓”） | `Sitemap: https://x.com/sitemap.xml` |

`Crawl-delay` 是**非标准**的（RFC 里没有，Google 明确不支持），只有 Bing/Yandex 部分认。

**③ 匹配用“最长匹配优先”**（RFC 9309 §2.3.1 原文：*the most specific match found MUST be used. The most specific match is the match that has the most octets*）

```
User-agent: *
Disallow: /shop/
Allow: /shop/sale/
```
`/shop/sale/x` 命中两条，`Allow` 更长（更具体）→ **放行**。等长时 `Allow` 优先。组内一条都不匹配 → **默认允许**。

**④ 错误状态码的语义是反直觉的（也是最容易写错的地方）**

| 服务器返回 | 爬虫该怎么做 | 依据 |
|---|---|---|
| 200 + 规则 | 按规则执行 | — |
| **4xx（404 等）** | **视同无限制，可以抓全站** | RFC §2.3.1.3 *crawler MAY access any resources* |
| **5xx（服务器挂了）** | **必须假定全站禁止** | RFC §2.3.1.4 *crawler MUST assume complete disallow* |
| 连续重定向 >5 次 | 当作不可用 | §2.3.1.2 |
| 缓存 | 不超过 24 小时 | §2.4 |

所以“我们服务器 500 了所以爬虫会随便抓”是完全反的 —— 5xx 期间是**全禁**。Google 的实现在 5xx 后会暂停抓取该站，30 天内继续用上一个正常版本。

**⑤ robots.txt 管“能不能抓”，不管“能不能被收录”**

这是 SEO 里最经典的坑：`Disallow` 掉一个页面，但如果别处有外链指向它，**它仍然可能出现在搜索结果里**（只是没有标题和摘要，显示为一行 URL）。想让它彻底不出现，得用 `noindex`（meta 标签或 `X-Robots-Tag` 响应头）—— 但你又不能用 `Disallow` 挡住爬虫，因为爬虫抓不到页面就看不到 `noindex`。正确做法是：**允许抓取 + 返回 noindex**。

LinkedIn 那份 robots.txt 就是这套东西的极致版：开头一段“Notice”声明只有**经批准的公开发搜索引擎**才被允许访问，70+ 个 UA 段分而治之，末尾给一个申请邮箱 `whitelist-crawl@linkedin.com` 和 `linkedin.com/legal/crawling-terms` 的链接。**它是“声明 + 申请通道”的组合，不是“默认欢迎”。**

## 三、他们和搜索引擎是“签约”的吗？—— 99% 不是，是默认的

**结论先说**：绝大多数网站**没跟任何人签任何东西**，Google 就来爬了。整个 Web 的抓取秩序建立在四层叠加的机制上，合同只在最外围、最少数场景才出现。

### 第 1 层：默认允许（opt-out 模型，这是根本）

**互联网的默认值是“公开即可访问”**，不是“需授权才可访问”。你上线一个博客，没有向任何人报备，Googlebot 第二天就来了 —— 因为它从别处的链接发现了你。

所以严格说：

> **robots.txt 不是“白名单”，而是“黑名单”。** 它不能给你授权（授权本来就有），它只能**收回**授权。

这也是为什么 `User-agent: *` 段在绝大多数网站上根本不存在 —— 不存在就等于全站允许。

法律层面同样：**robots.txt 是“技术声明”，没有法律强制力**。它既不构成合同，也不是法律。它之所以被遵守，是因为（a）主流爬虫都是商业公司，不想惹麻烦；（b）不遵守会被封 IP/被起诉。

### 第 2 层：机器可读的“事实标准”——**用协议替代合同**

这一层是重点，因为它们才是“协议”的真正含义：**双方各自实现同一套约定，不需要任何一方签字。**

| 机制 | 方向 | 谁在用 |
|---|---|---|
| `robots.txt`（RFC 9309） | 站方 → 爬虫：**别抓** | 全行业 |
| `<meta name="robots" content="noindex">` / `X-Robots-Tag` | 站方 → 爬虫：**别收录** | 全行业 |
| `sitemap.xml` | 站方 → 爬虫：**请来抓这些**（带 lastmod） | 大站标配 |
| **IndexNow** | 站方 → 搜索引擎：**这个 URL 刚变/新增/删了**，即时推送 | 2021 年 Bing + Yandex 推出，Bing/Naver/Seznam 支持 |
| **Google Indexing API** | 站方 → Google：主动推送，职位页（JobPosting）和直播页专用的优先通道 | 招聘站/直播站 |
| `llms.txt` | 站方 → AI 爬虫：结构化说明哪些内容给 AI 用 | 2024 年新提，**尚未成为标准** |

**IndexNow 和 Indexing API 这类“推送协议”对你的消息推送有直接启发**：它们证明了**“等别人来爬”是最差的方案，主动推送才是最优解**。这也是为什么我在上一条里说信息源要分 A/B/C 级 —— A 级（有 RSS/API/推送）的核心优势不是“稳定”，而是**你不需要抓取，你在收通知**。

### 第 3 层：真正“签约”的少数场景（钱和独家内容介入的地方）

| 场景 | 例子 |
|---|---|
| **付费授权** | Google News Showcase 向出版商付费；欧盟《数字单一市场版权指令》的邻接权；澳大利亚《新闻媒体议价法》 |
| **API 商业合同** | Reddit 2023 年 API 收费、X/Twitter API 涨价、Stack Overflow 与 OpenAI 的数据授权 —— 这才是“签约” |
| **白名单准入申请** | LinkedIn 的 `whitelist-crawl@linkedin.com` + Crawling Terms（要审核，是半正式准入） |
| **互惠默契（无纸面）** | 搜索引擎 ↔ 内容平台：你让我收录，我给你导流。这是**利益交换**，不是合同 |

### 第 4 层：法律兜底 —— hiQ v. LinkedIn 案值得你记住

你问的正是 LinkedIn，这个案子是全网最相关的判例：

- **CFAA 层面（刑事/“黑客行为”），hiQ 赢了**：第九巡回法院认定**抓取公开可访问的数据不构成“未授权访问”**。也就是说，抓公开网页本身不是犯罪。
- **合同法层面，hiQ 输了**：地方法院认定 hiQ **违反了 LinkedIn 的用户协议（User Agreement）**，2022 年底双方达成和解。

所以那句总结是对的：

> **“公开可访问” ≠ “可以随便抓”。** 约束不是来自刑法，而是来自合同法和服务器封禁。

而这也解释了 Google 和你的本质区别：**你被抓是“违约”，Google 被抓是“不存在违约”——因为它被允许了。**

## 四、落地到你的采集层（三条硬要求）

1. **必须完整实现 RFC 9309 语义**，尤其 **5xx = 全站禁止** 这条。很多自己写的爬虫把 5xx 当成“随便爬”，这是最容易被抓的违规点。
2. **URL Frontier 用优先队列，不用 BFS 的 FIFO**。BFS 只负责“新域名的首次发现”（保证不遗漏栏目），一旦探明站点结构，就切到“按变更率排序的增量重访”。
3. **能拿推送就不轮询**。sitemap 的 `lastmod`、RSS 的 `pubDate`、IndexNow 式的推送接口，优先级都高于“定时全量抓”。你的推送系统 90% 的成本和 100% 的延迟问题都出在“用轮询模拟推送”这件事上。
