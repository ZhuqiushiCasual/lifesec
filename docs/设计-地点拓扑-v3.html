selfsec · 设计稿 v3

地点只有一个表，邻居只有一个查询

用你的三条原则 review 上一版：能算出来的东西不要存；一个能力不要长出两个方向；元数据长一格，关系就多一层。

状态 设计稿，未开发 承接 设计-推荐线.md → 设计-地点拓扑-v2.md → 本稿 新增持久化 一张表 新增查询 一个函数

整件事收敛成 一张 places 表 + 一个 nearby(anchor, want) 函数。

餐厅和玩点是同一张表里 category 的两个取值，不是两种东西。所以「餐厅 → 餐后闲逛」和「玩点 → 就近吃」是同一行代码，只是 want 不同——我上一版还留着一个「方向」的概念，那是多余的。

地点之间的距离、同商场、同地铁、同一篇笔记提到过，全部在查询时算，不落库。
拓扑不是存下来的图，是节点属性算出来的结果。属性可扩展，拓扑就自动长大。

这一版没有的东西

没有图数据库，没有边表（place_edges），没有意图配置表，没有配方反馈表，没有重算任务，没有人工置边，没有模型调用。

01 用你的思路 review 上一版

你的判断是：越简洁越好维护，也越强大。拿这条尺子量 v2，有五处是我自己加出来的复杂度。

v2 的做法问题这一版
place_edges 边表 距离、同商场、同区域都能算出来，存进去就要同步、要重算、要处理「人工边不被覆盖」。
为可计算的东西建存储，是纯负担。		 边全部在查询时算。步行分钟 = 直线距离 × 1.3 ÷ 80 米/分；同 parent_place_id 一律按 2 分钟。
四层架构（节点 / 关系 / 意图 / 配方） 层是给不同变更频率的东西划边界用的。这里节点和数据一起变，配方只是一个函数，硬划四层让图好看，代码并不会变好懂。 两个东西：数据（places）和查询（nearby）。配方是调用查询的一段组合逻辑，写在一个文件里。
「方向」：recipe(line) vs recipe(stroll) 方向是组合层面的说法，不是数据结构里的说法。有方向就会出现两套代码、两套测试、两份文案。 没有方向。只有一个 want 参数（想吃 / 想逛 / 想室内）。两个场景共用同一个函数与同一段理由模板。
意图配置表 / 配方注册表 现在只有 3 个意图。配置表是给「运行时要改」的东西准备的，这里改代码更快、更可读，还能被 IDE 和测试覆盖。 3 个 want 写成一个字典常量，等真到 10 个再抽象。
recipe_feedback 表 「不想去」现有两张表已经有 hidden 字段，再建一张表是为了记录一个布尔值。 直接复用 hidden。降权、收藏这类信号等有真实行为数据再说。
拆掉之后付出的代价，我承认

① 每次请求都重算邻居（39 个节点，一次全表 + 一次排序，毫秒级，可接受）；② 距离是估算，街上绕路会让「约 6 分钟」有误差（卡面写「约」，不写「6 分钟」）；③ 没有人工置边，配错了只能改坐标或分类，不能手工「我知道这两个近」。第三条是唯一真实损失，我认为在几十个点的规模上不值得为它建一张表。

02 数据：一张表装下所有地点

餐厅和玩点的差别，几乎全是属性的差别，不是结构的差别：人均、菜系、口味；门票、耗时、适合季节。既然要「元数据可不断拓展」，那就别让这些差异长成列，而是一起装进一个可扩展的 JSON。

-- 新表，只此一张
places
  id               uuid pk
  canonical_key    varchar unique   -- 规范化(名+分店)，回填脚本靠它幂等
  name             varchar(120)
  branch           varchar(80)
  category         varchar(16)      -- eat / play / shop / park / exhibit / street
  area             varchar(40)
  address          varchar(255)
  lng, lat         double null      -- 可空：查不到就不假装有
  metro_station    varchar(80)
  metro_walk_m     int

  created_at, updated_at

为什么不再合并 date_menu / outing_spots

这是唯一一个我主动选择不做的简化。合并成一张表在模型上更干净，但它会牵动 11 个后台接口、挑餐厅页、照片表的 restaurant_id、以及 plans.ref_type 里两种取值——这是一次纯重构，收益是「少两张表」，风险是打断一个已经在用的功能。

所以我选中间态：places 是拓扑的唯一入口，领域表保留自己的业务字段，加一列 place_id 挂上来。删除旧表这件事，等哪天要重写挑餐厅页时顺手做。

表管什么变化
places在哪、是什么、有哪些属性、和谁同一个 parent新增
date_menu菜单顺序、口味三轴、点菜避坑、实拍图加 place_id
outing_spots候选顺序、一句提示加 place_id
plans安排落库不动（ref_type 仍是 date_menu / outing_spot）
date_photos实拍图集不动

03 拓扑：边是算出来的，不是存起来的

算距离，只需要三个分支

def walk_minutes(a, b):
    if a.id == b.id: return 0
    if a.parent_place_id and a.parent_place_id == b.parent_place_id:
        return 2                      # 同一个商场：不按坐标算，否则会得出「相距 0 米」
    if a.lng and b.lng:
        return round(haversine_km(a, b) * 1.3 * 1000 / 80)   # 绕路系数 1.3，步速 80 m/min
    return None                       # 没有坐标：不进候选，不编距离

属性长一格，拓扑就多一层

这是「元数据形成拓扑」真正落地的地方：不需要写迁移，也不需要重算任何东西，新属性下次查询就生效。

新加的元数据自动多出来的关系用在哪
attrs.indoor「雨天能去哪」下雨的周末推室内候选，室外自动降权
attrs.open_till「晚上十点后还能去哪」吃完饭 21:30 找地方坐，过滤掉已关门的
metro_station「同站直达」两站之间不用打车，同站换乘等于 0 距离
parent_place_id「同一栋楼里」商场里的店 / 餐厅，都在 2 分钟半径内
attrs.duration_min「够不够时间」下午 3 点出门，排得下 90 分钟的展，排不下半天

04 查询：一个函数，没有方向

你说得对——餐厅到闲逛、闲逛到餐厅，在底层是同一件事。锚点是一个地点，want 是候选的类别，这两个参数已经够描述所有方向：

async def nearby(db, anchor_id, want=None, max_walk=15, limit=5):
    """以 anchor 为中心，返回走得动、符合 want 的邻居。唯一的推荐入口。"""
    anchor = await get_place(db, anchor_id)
    rows = await db.scalars(select(Place).where(Place.hidden.is_(False)))
    out = []
    for p in rows:
        if p.id == anchor.id: continue
        if want and p.category != want: continue
        m = walk_minutes(anchor, p)
        if m is None or m > max_walk: continue
        out.append({"place": p, "walk": m, "score": score(anchor, p, m, want)})
    out.sort(key=lambda x: (-x["score"], x["walk"], x["place"].id))
    return out[:limit]

餐厅 → 餐后闲逛

nearby(
  anchor_id="叶马茶楼",
  want="play"
)

→ 天目里 约 6 分钟
→ 美院象山 约 12 分钟

玩点 → 就近吃

nearby(
  anchor_id="天目里",
  want="eat"
)

→ 叶马茶楼 约 6 分钟
→ 新白鹿 约 8 分钟

同一段代码、同一套打分、同一个理由模板。区别只在 UI 上默认选中哪个 want 标签——那是界面的事，不是数据的事。

打分：四项，可解释，可复现

score = 0.40 * near + 0.30 * fit + 0.20 * habit + 0.10 * area

near   = 1.0 (≤5 min) / 0.8 (5–10) / 0.5 (10–15) / 0.9 (同商场)
fit    = want 要求的 attrs 命中率，如「逛」要 街区/公园/书店/平路
habit  = 去过 +1，没去过 0（熟悉的先来，避免每次都推没去过的）
area   = 同区 0.5，跨区 0

排序键固定为 score desc, walk asc, id asc——同分不抖，测试可断言。全程不调模型：模型只用来补 attrs（这座公园要不要爬坡、这家店几点关门），不参与排序。

理由句是拼出来的

每个候选必须能说清「凭什么」，否则不展示：

# 模板：从 {anchor} 走 {m} 分钟到 {name}，{tags[0]}，{一句来自 attrs 的说明}
"从叶马茶楼走约 6 分钟到天目里，街区，书店和咖啡都在里面"
"从西湖走约 10 分钟到新白鹿，江浙菜，人均 90 的那家"

缺字段就少写一段；写不出具体信息的候选直接不出现，绝不出现「离你很近」「环境不错」。

05 上层：推荐线是两个 nearby 拼起来的

上一版的「配方层」在这里没有位置——它不是一个层，就是一段十行的组合逻辑：

async def line(db, play_id):
    play = await get_place(db, play_id)
    eats = await nearby(db, play_id, want="eat", max_walk=15, limit=3)
    if not eats: return {"play": play, "eat": None}   # 没配到餐厅，照样能安排出门
    return {"play": play, "eat": eats[0]["place"]}

以后要「一天三段」「雨天备选」「带爸妈」，都是在这一层再写一个函数，底层不动。反过来，底层加一个 attrs 键，上面所有组合自动变聪明。

不落 outing_lines 表

它是计算结果。「安排」落 plans（现有接口，幂等），「不想去」写 hidden（现有字段）。派生结果不建表，就不会有状态对不齐的问题——上一版把「不想去」记在线上，线重算后 id 变了，状态就失联了。

06 界面：一个浮层，一组标签

现在「这个地点周围有什么」这件事，在挑餐厅页、安排页、#experience 浮层各写了一遍。收敛成一个组件，所有入口都调到同一个地方：

┌ 叶马茶楼 ────────────────────────────── × ┐
│ [实拍]  西湖区 · 江浙菜 · 人均 120          │
│ 上榜理由：…………………………………………      │
│                                            │
│  [饭后走走] [就近吃] [雨天室内]              │  ← 标签 = want，默认选哪个由入口决定
│ ────────────────────────────────────────── │
│  天目里        约 6 分钟 · 街区 · 书店咖啡    │
│  美院象山      约 12 分钟 · 校园建筑         │
│ ────────────────────────────────────────── │
│  [安排这一天]        [不想去]                │
└────────────────────────────────────────────┘
  • 餐厅详情默认选中「饭后走走」，玩点详情默认「就近吃」，其余完全一样；
  • 「安排这一天」落到现有 plans：一条 ref_type=outing_spot，一条 ref_type=date_menu；
  • 安排页顶部的「这周去哪」保留，卡片可下钻到这个浮层。
不做

不做地图、不做导航跳转、不做月历、不在卡片里写「离你很近」、不把笔记里的店自动塞进菜单。

08 落地：四步，每步都能验

  1. 建表 + 回填　places 上线，27 + 12 个节点入库，领域表写回 place_id。此时老功能完全不知道它存在。
  2. 补坐标　一次性脚本，查得到的写 lng/lat，查不到的留空；缺坐标的点自动降级为「同区」，不崩。
  3. 上线查询 + 浮层　餐厅详情出现「饭后走走」，玩点详情出现「就近吃」。这一句就是 P1 的全部价值。
  4. 推荐线　安排页顶部从 line() 取数，卡片下钻到浮层。

验收（P1）

  • 任一餐厅详情能看到至少 1 个餐后闲逛候选，带「约 N 分钟」；
  • 任一玩点详情能看到至少 1 个就近吃饭候选——同一段代码、同一个测试；
  • 同一输入两次请求，顺序完全一致（不依赖模型、不依赖字典序随机）；
  • 缺坐标的店不报错，降级成「同区」，卡面不写分钟；
  • 没有候选时显示「附近没找到合适的」，不编造；
  • smoke_test.py 全绿，新增 places 段落。

09 还剩两件要你定

  1. 坐标来源：V1 用 OSM 免费（省事，小馆子可能查不到，缺少的退成「同区」），还是现在去注册高德 key（准，多一步配置）？我倾向先用 OSM，把缺的记成清单，值不值得为 10 家店配 key 到时候再说。
  2. 节点数量：现在 27 家餐厅 + 12 个玩点。图太稀，推荐会重复。要不要在 P1 顺手把玩点补到 40 个左右（从你现有的收藏和笔记里提，不用抓小红书）？
